# v2026.38.1 — CalVer numbering, and a database compatibility reset

This is the first CalVer release. The version number is a date-shaped series identifier now
(`YYYY.W[.R]`: the ISO week-numbering year, the UTC ISO week the series starts in, and an optional
revision);
nothing about the product changed because of the number itself.

## Compatibility boundary

**This release requires the v0.4.72 database schema. Legacy databases cannot be opened directly.**

All historical upgrade code has been removed from the application: there is no `ALTER TABLE` that
adds a missing column, no report-version backfill, no per-release-line adoption step, and no stamping
of a database that already exists. What used to be a migration is now an acceptance check — every
table, column and index the base schema declares must already be present, and a database that fails
it is refused *before any statement runs*, with the release it has to be taken through named in the
message.

- **A database at the v0.4.72 shape starts exactly as it did before.** No migration, no DDL, no
  writes; a rollback to v0.4.72 is clean.
- **Anything older is refused.** Take it through the legacy releases first — v0.2.26 for a pre-v0.2
  database, then each line's last release — until v0.4.72 has started it once.
- A backup from an older release is refused too, and for the same reason: its columns do not cover
  the current schema, and loading it would silently produce rows that never had the data.

The schema itself is unchanged. This is a boundary about what the runtime is willing to read, not a
new shape.

## Installation and transition

- **Fresh installation:** nothing to do. A new database is created complete and stamped.
- **Existing data:** [docs/releases/README.md](README.md) carries the transition runbook — stop the
  portal, take a consistent backup with `report-portal backup` (a raw copy of a live SQLite file is
  not adequate), start the database once with **v0.4.72**, verify, then start this release. Keep the
  v0.4.72 binary or its `ghcr.io` image tag retrievable: it is the bridge, and the rollback route.
- **Configuration and key material:** keep `config.yaml` and `secret_key`. SSO secrets and the SAML
  keyring are sealed with `secret_key` and cannot be decrypted without it.

## Changed

- Release tags are `vYYYY.W[.R]`. `scripts/tag-release.sh` validates the shape (including whether the
  selected year actually has an ISO week 53) and takes the tag annotation from the tagged commit
  rather than from the working tree. The revision may be left off for the first release of a week;
  `v2026.38` and `v2026.38.1` are then two different numbers rather than two spellings of one.
- Maturity is GitHub Release metadata and never the tag. The release workflow prepares a **draft**
  with the archives, `SHA256SUMS.txt`, and the image digest recorded; a new "Release channels"
  workflow owns `:latest` and `:beta` and moves them by re-pointing at the published digest, so a
  promotion does not rebuild anything and an old-series patch cannot displace a newer release.
- The footer and the management rail show the product version as `2026.38.1` rather than the git tag
  `v2026.38.1`. `/api/version` and the backup header still carry the tag verbatim: it is the build's
  identity, and the SPA compares it to notice a deploy or a rollback.
- Restore no longer accepts a dump whose columns do not cover the current schema, and no longer
  accepts a dump with no recorded schema generation. Both are refusals before the destructive step.

## Removed

`internal/app/upgrade_v04.go` in full, the additive column reconciliation in `ensureColumns` (now a
read-only shape check, `verifyBaseSchema`), and the report-version backfill and identity-index
rebuild in `reconcileReportVersions`. See
[ADR 0034](../adr/0034-calver-baseline-and-database-compatibility-reset.md) for the boundary and the
reasoning, and ADR 0013, which this supersedes in part.

## Future upgrades

A direct-upgrade support policy starts with this baseline: for a target full release at T, upgrades
are supported from full releases in this family first made stable within the preceding 12 calendar
months. Product year/week changes do not retire migrations; retirement is deliberate, and a retired
chain has to be published as a tested bridge first.

## Rollback

Restore the **v0.4.72** binary or image against the retained pre-cutover database and configuration.
Do not open the post-bridge database with an older binary.
