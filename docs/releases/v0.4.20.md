# v0.4.20 — the cleanup history records deletions, not days

## Upgrade notes

From v0.4.3 or later — pull and restart. No schema change.

The cleanup history will look emptier, and on most portals it will disappear entirely. Nothing was
deleted: rows written by earlier builds are filtered from the list, not removed from the table. See
below for why.

## Fixed

**A scheduled pass that deleted nothing wrote a history row anyway.** On a portal whose retention
targets never match — which is every portal running the shipped defaults, since every target ships
disabled — the console showed one identical `0 · 0 · 0 · 0 · ok` row per day and nothing else.

The row count is not the real damage. `cleanup_runs` is a ring buffer, so a row a day **evicts the
only rows the table exists for**: the pass that actually deleted somebody's report. A log of
destructive operations that discards the destructive operations is worse than no log, because it
still looks like one.

A pass is recorded when it deleted something or when it failed. A failure deleted nothing either,
and it is precisely what an admin needs to see. The last-run stamp is still written every pass, so
"the scheduler ran and found nothing" stays on the page — that fact belongs in a stamp, not in a row
a day.

Rows written before this release are **filtered on read, not deleted**. A retention log is the last
thing to go rewriting, and there is no reason to touch the table to fix a display. They age out of
the ring on their own as real events arrive.

The history card is absent until there is something in it, rather than showing an empty table under
a heading.

## Changed

**The history table paginates**, ten rows to a page, with the pager hidden until there is a second
page. It rendered every row it had, so anything below it was a long scroll away.

**The retained history and the readable history are one constant.** They had drifted — 200 rows kept
against a hard-coded read of 50 — so three quarters of the table was rows nothing could ever show. A
test now fails if a default list cannot reach every row the ring keeps. Both are 200: how many rows
appear at once is the table's business, and it paginates.

[ADR 0017](../adr/0017-storage-cleanup.md) recorded "one row per real pass" as a decision, so it is
amended rather than left to mislead whoever changes this next.

## Verification

Go and web suites (310 web tests), vet, gofmt, both builds, and `scripts/e2e_check.py`.

Two new Go tests: a no-op pass writes no history but still writes the last-run stamp, and rows left
by earlier builds are filtered from the list without being deleted from the table.
