# v0.4.24 — a character that has no font stops the build, not the reader

## Upgrade notes

From v0.4.3 or later — pull and restart. No schema changes, nothing to run by hand, and rolling
back to v0.4.23 is clean: everything here lives in the image and in which font draws which glyph.

**The image gains about 2 MB** (one monochrome emoji font, plus DejaVu named explicitly where it was
already resident). Reports that used ballot boxes, dingbats or emoji will render more characters
than before, so a report exported across this upgrade can reflow.

**If you build the image yourself**, the build now makes a third pinned fetch (`raw.githubusercontent.com`,
sha256-verified) and ends with a coverage gate that fails the build rather than shipping an image
that would silently drop characters. A build host with no route to that host fails at the fetch.

## Fixed

**Characters with no font did not fall back — they vanished.** wkhtmltopdf draws nothing at all for a
codepoint no installed font covers. Not a tofu box, not a warning, not a log line: the character is
simply absent from the page, and the only place the failure is visible is the finished PDF. ✅, ❌ and
🔴 were among the casualties, because the image installed exactly one font and it does not carry them.

The image now installs coverage on purpose instead of by accident. **Noto Emoji** is added — the
monochrome outline build, pinned by commit and sha256-verified. The colour builds were measured and
rejected, and the reason is worth stating because it is a trap: a colour emoji font embeds into the
PDF cleanly and reports as embedded, while painting nothing. The bitmap build keeps its ink in CBDT
strikes and the newer build keeps it in COLRv1 layers; PDF has no concept of either, and both leave
the base glyphs empty. **fonts-dejavu-core** is now named in the apt line. It was already in the
image, but only because `fontconfig-config` happens to list it first in an alternation — and it is
the sole provider of 72 codepoints in the corpus below, including every superscript and subscript.
Coverage that load-bearing should not depend on how apt resolves an alternative.

Noto Sans Symbols 2 was evaluated and **not** shipped. It adds no coverage the other fonts lack, and
it rendered U+2611 ☑ 40% smaller and 42% lighter — a regression against the complaint that prompted
this work.

**Chart labels and body text could resolve to different faces.** The font stacks in the PDF template,
the Mermaid chart sanitizer and the browser-print fallback now all name the same faces in the same
order, and a test fails if they drift apart. Worth being precise about what this buys, because the
mechanism is easy to state backwards: the stack pins **precedence**, not availability. fontconfig
falls back to any installed font whatever the stack ends with — verified by rendering with each font
set in turn, where installing only the CJK face makes every symbol disappear under either stack.
Naming the faces is what stops DejaVu winning a glyph the CJK face already has.

## Added

**A build-time glyph-coverage gate.** `scripts/font-coverage-corpus.txt` lists 623 codepoints an
exported report can plausibly contain — ballot boxes through box-drawing, Greek finance variables,
CJK punctuation, currency, emoji — each tiered `require`, `advisory` or `nonprinting`.
`scripts/probe-font-coverage.sh` checks that list against the fonts fontconfig can actually resolve
and fails the build on a gap.

It runs inside `Dockerfile.release`, which is the only place the answer is meaningful: a GitHub
runner carries DejaVu, Liberation and a colour emoji font of its own, so the same check passes there
while the image ships broken. The release job now waits on the image build too, so a coverage failure
stops the tag instead of arriving after the Release is already published.

The filter is `outline=true` **and** `color=false`, and both halves are load-bearing. Selecting on
outlines alone excludes the bitmap colour font but not the COLRv1 one, which has real outlines and
empty base glyphs; without the colour term it passed all 623 codepoints while ✅ ❌ 🚀 ⭐ each
rendered zero ink.

Exercised in five scenarios: the shipped set passes (623 checked, 6 advisory); the bitmap colour font
fails with 70 missing; the COLRv1 colour font fails with 70 missing; removing DejaVu fails with 98
missing; an image with no fonts refuses to pass a vacuous check.

Six rare currency signs (₶ ₷ ₻ ₼ ₾ ₿) are covered by nothing in the set and are marked `advisory` —
reported on every build, failing none. That tier exists so a deliberate gap stays visible instead of
being deleted from the list.

## Known gaps

**Preformatted blocks are set in a proportional font.** `<pre>` inherits no font-family, so the UA
default `monospace` applies and resolves, in this image, to a proportional face. ASCII and
box-drawing tables therefore have ragged edges. Fixing it properly needs a CJK monospace font whose
ideographs are exactly twice the Latin advance — Noto Sans Mono CJK SC measures 0 px of drift where
today's set measures 140 px — and that font is 16 MB, about 12% on the image.

It is deliberately not in this release, because the tables in real reports are **also** ragged for a
second reason no font can fix: their lines are not equal width to begin with (a sample measured
56/50/47/47/84 half-cells). Shipping 16 MB now would produce no visible improvement in a real report
and could not be verified against one. The generator's width computation is the first fix; the font
is a clean follow-up once alignment is observable.

**Symbols are smaller and lighter than the text around them.** This is Noto Sans CJK SC's own drawing
— → is 0.56× the height of an adjacent ideograph, ✓ carries 0.25× the ink — and the first font in the
stack wins, so no fallback font can change it. Correcting it means intervening in the markdown
pipeline, which is a different kind of change than this one.

## Verification

Go suite, web typecheck, 323 web tests and the SPA build (this project has no lint step), plus vet
and gofmt.

The gate was verified by running it, in five font environments built with scratch fontconfig files,
against the real corpus — including fetching both colour emoji builds and confirming each is refused.
Coverage itself was established by rendering all 623 codepoints one per page through wkhtmltopdf and
counting ink: 594/594 `require` drew ink, 23/23 `nonprinting` drew none, 6/6 `advisory` drew none.
The end-to-end path was exercised through `renderPDFHTML` into `htmlToPDFContext` rather than a
hand-built sample; the output embeds Noto Sans CJK SC, Noto Emoji and DejaVu Sans and draws every
test symbol.

Two claims made earlier in this work were wrong and were corrected by measurement rather than left
standing: that the font stack's trailing generic was what enabled fallback (it is not — installation
is), and that selecting on outlines alone was enough to exclude colour emoji fonts (it is not — that
is what the `color=false` term is for).
