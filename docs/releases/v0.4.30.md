# v0.4.30 — the audit log answers the questions it is asked

## Upgrade notes

From v0.4.3 or later — pull and restart. No schema changes and nothing to run by hand. Rolling back
to v0.4.29 is clean.

**Lines written before this release keep the shape they were written in.** Nothing is rewritten:
reads recorded earlier still have no address, and runs recorded earlier still carry only the
target's id. The console renders both old and new lines, so an old line simply says less.

**The detail column is rendered rather than printed verbatim.** The stored JSON is unchanged and is
still what the filter and any export work against; what changed is that the console composes it
into a sentence. The exact payload is one click away on every row.

## Fixed

**A report read did not record where it came from.** `recordReportRead` never took the request —
every other writer goes through `recordChange` or `recordAuth`, which stamp the address — so the one
action most likely to be the subject of "who saw this, and from where" was the only one that could
not answer the second half of it.

**`auth.step_up` had no label.** The console renders an action through its translation and falls
back to the raw string, so the filter offered `auth.step_up` in a list of translated phrases.
Nothing failed; it just looked unfinished until somebody read it. A test now checks the whole action
vocabulary against every locale bundle — the vocabulary lives in Go and the labels in JSON, which is
exactly how one goes missing.

**A run recorded that a decision happened, not what was decided.** `run.submit` stored a target id, a
row count and a priority. It now records the workflow by name, the inputs, and the options actually
chosen: schedule, preset window, retries, notify. The inputs are clamped per value and in total,
because an agent run carries its whole prompt and the log is a record of the decision, not a
transcript of it.

## Changed

**The detail column is written for the person reading it.** "Who read what" used to arrive as
`{"date":"2026-08-10","symbol":"000909","title":"000909 restructuring sentiment"}` — every field the writer
stored, in the order a serialiser chose. It now reads `000909 restructuring sentiment · 2026-08-10`, and
a run reads `Ran <workflow> · symbol=603587 · priority=30 · retries=1`.

Three rules keep that from costing anything. Fields the renderer does not recognise are still shown
as `key=value`, because a renderer that silently drops what it has not been taught is worse than the
JSON it replaced. Fields that say nothing are left out — an unset schedule, a flag that did not
fire, the numeric id of something the line already names in words. And an empty list says it is
empty rather than printing as though the field had no value, which is the whole point of half of
all grant-change lines.

## Added

**Every row opens in full.** Scanning the log and investigating with it want opposite things from
the same table, so the rendered column serves the scan and a button at the end of each row opens the
record whole: when, who (with the OU they were in at the time), from where (with the region), which
action — both its label and the raw action string the API filters on — which object, the rendered
detail, and the stored payload verbatim, with a copy control for pasting into a ticket.

The payload is bounded and scrollable. A grant change across a large OU can carry a long list, and a
dialog taller than the window is one nobody can close.

## Verification

Go build, vet and gofmt; the Go suite; web typecheck, 361 web tests and the SPA build.

The rendering was compared against the old column side by side in a browser, on the real shapes:
a report read, a run submission carrying a long prompt, a grant change with an empty side, and an
SSO sign-in.

The two SSRF pre-check tests noted in v0.4.25 still fail on a machine whose resolver answers every
name; unrelated to this release and green on CI.
