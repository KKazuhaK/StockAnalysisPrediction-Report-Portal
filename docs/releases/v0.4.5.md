# v0.4.5 — organizational units you can actually read

## Upgrade notes

From v0.4.3 or v0.4.4 — pull and restart. No schema change, and sessions
issued by the old build keep working; both paths were verified by upgrading a
database in place. From v0.4.1, the portal still refuses to start and says so.

## Changed

Organizational-unit management is now pick-one-and-see-it. A flat list of
every OU, a modal of ten fields, and a second modal hidden behind a small icon
became the same tree that scopes the account list, with one OU's whole
configuration beside it, in sections that separate what an OU IS from what its
members may DO. Creating one asks for a name and a place; everything else
already has a sensible inherited value the moment it exists.

Inheritance says what it inherits. Four switches all labelled "inherit from
the default group" sat above the fields they gated, so none said what it
inherited or which field it belonged to — and a greyed-out field showed no
value, except the run window, which kept its placeholder "9-18". That is the
EXAMPLE from the hint text, so an inheriting field displayed something that
read exactly like a value. Each setting is now one line naming the value it
would inherit and where that comes from, with the override input present only
when chosen. Three different sources those four identical labels had
flattened into one: run governance falls back to the Default group, the daily
quota to the parent OU, and priority to the system default.

## Fixed

The urgent tags contradicted each other. "2 tickets/period · inherited" and
"unlimited urgent" were rendered by independent conditions, so an OU
inheriting a ticket count while setting unlimited itself showed both. The
policy is a three-way choice and is now resolved to one answer before anything
renders it.

Server error messages were not translatable, in both directions: an English
login page printed 用户名或密码错误 and a Chinese one "captcha is required or
incorrect", because the response is written before the browser's language is
known. Every error now carries a stable code the UI renders through t(),
falling back to the server's own wording for a code the bundle does not know —
so an older UI against a newer server degrades to English, never to a bare
translation key.

The web suite had two flakes wearing the same clothes. Failures roaming
between four files were CPU contention: vitest fanned out to every core and
the suite raced itself. The one that survived that fix was real and specific —
document.title is written by a passive effect, one commit behind the DOM the
waitFor was watching, so asserting it synchronously read the previous commit's
value about one run in twenty. Both fixed; 0/40 on the test that used to fail.

## Verification

v0.4.3 and v0.4.4 binaries.
