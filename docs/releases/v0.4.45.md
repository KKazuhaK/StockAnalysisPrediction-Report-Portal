# v0.4.45 — live quotes, a database you can copy, and a portal you can use without a mouse

One release rather than nine. The work below landed on two branches that ran beside each other and
merged together, and none of it was ever built or shipped separately — so it is one version, and the
eight interim numbers those branches used along the way do not exist.

## Upgrade notes

From v0.4.44 — pull and restart. **One additive column** (`cleanup_runs.bytes_reclaimed`), picked up
automatically at startup. No migration, nothing to re-enter.

Four things worth knowing before you do:

**Take a backup.** The command exists as of this release, and it is the first release in which it
does:

```bash
docker compose exec report-portal /app/report-portal backup - | gzip > dump-$(date +%F).gz
```

Keep the `./config` directory beside it. `secret_key` lives there and is deliberately *not* in the
dump, so a backup without it restores everything except working SSO.

**Docker users get two behaviour changes for free**, both from the image and the compose file. The
container now has a `HEALTHCHECK`, so `docker compose ps` starts showing the portal as `healthy` /
`unhealthy` where it previously showed nothing — and unhealthy means its database is unreachable. And
`stop_grace_period: 15s` is set on the portal service; if you run your own compose file, add it,
because Docker's 10s default can `SIGKILL` the portal in the middle of the graceful shutdown this
release added.

**`report.ingested` now also fires for reports written or edited in the browser**, and its payload
has gained `version`, `author` and (on the v1 ingest path) the same `created` flag it already had.
Existing subscribers keep working; they will simply start hearing about reports they were never told
about before.

**Your logs will get busier**, on purpose: API failures, every API mutation, and anything slower than
a second now appear where previously they appeared nowhere. Routine polling stays quiet, so the
volume should be small — but it is a change in what `docker compose logs` shows.

Two smaller ones. An authenticator entry enrolled before this upgrade keeps its old label (see
*Settings that were read and never written*). And the portal now makes outbound requests to
`web.ifzq.gtimg.cn`, `qt.gtimg.cn`, `hq.sinajs.cn` and `money.finance.sina.com.cn` when somebody
opens a stock page; the first two were already reached at ingest for company names, and where they
are unreachable the quote panel says so and the report renders as before.

Rolling back to v0.4.44 is clean. The one additive column is ignored by the older build, and the
quote panel simply disappears — it stores nothing.

## Added

### Live quotes and a daily candlestick chart on the reading page

The stock page now opens with the stock, not only with what was written about it: last price,
change, the vendor's percentage, open, previous close, high, low, volume and turnover, stamped with
the vendor's own clock and the source that answered. Under it, a hand-rolled SVG candlestick chart
with a volume panel over one month to a year, navigable by keyboard. It sits above the timeline
because it describes the company; the report's own actions stay in the report's card.

Nothing is stored and no background loop was added: a quote lives in a bounded in-memory LRU for
between thirty seconds and five minutes, with the TTL taken from the exchange session the vendor
itself reports rather than from a trading calendar this repo would have to invent and then maintain
through every holiday and half-day. Concurrent readers of one code collapse into one upstream call,
and a semaphore caps how many can be in flight, so a link shared into a group chat is one fetch and
not fifty.

Tencent's `fqkline` endpoint is primary because a single call returns the daily series, the live
snapshot **and** the session state together, keyed by the `sh`/`sz` prefix the name fetch already
computes — three answers that cannot disagree about which instant they describe. Sina is the
fallback. eastmoney, the vendor this codebase already talks to for names, was measured and rejected:
its history endpoint answered with an empty body and it wants a numeric id we do not have.

Four decisions that are cheap now and expensive later:

- **Every price is an integer number of 分.** The schema declares 222 `TEXT`, 61 `INTEGER` and 24
  `BIGINT` columns and not one `REAL`, and `REAL` is an 8-byte double on SQLite and a 4-byte float on
  Postgres.
- **The percentage is the vendor's own string, rendered verbatim.** Recomputing it from last and
  previous close prints a fake double-digit crash on every ex-rights day. Sina is the exception — it
  publishes neither number, so on that path both are ours — and [ADR 0028](../adr/0028-live-quotes.md)
  says so where the promise is made rather than leaving a reader to discover it.
- **The chart is 不复权.** Front-adjusted history is re-based by every dividend, so a bar cached in
  July is a different number in December.
- **The Beijing exchange gets a price and no chart, deliberately.** Tencent returns an empty daily
  array for `bj830799`; Sina's series for the same code stops sixteen months back while the live
  price is 34.28. Stale data that looks like data is worse than none, so the panel says the market
  has no history instead of drawing an empty frame that reads as a flat line at zero.

The drift gate is the part that earns its keep. These are positional index reads over bodies with no
schema and no changelog, and the realistic failure is a vendor inserting one field — after which
every range check still passes and the portal renders a confident wrong price. What survives that is
an arithmetic identity: the vendor's percentage has to agree with its own last and previous close.
Around it sit an exact code echo at a known index, per-candle ordering, a field-count floor (39, not
an equality against 88 — the captured Beijing response carries 87), and a range check that skips
itself when high or low is zero, because that is what a suspended stock looks like. There is
deliberately **no** band on the size of the move: A-share limits are ±5/10/20/30% by board and a
first-day listing has none, so any band wide enough to keep a real limit-up day is too wide to catch
anything.

### `backup` and `restore`

Everything the portal owns is rows: accounts, groups and the OU tree, report bodies, the
hand-written versions and their revision history, installed apps and their files, tokens, webhooks,
recurring tasks, and every setting that is not one of the six lines in `config.yaml`. There was no
way to take a copy of any of it and no way to put one back — not a command, not an endpoint, not a
paragraph.

That was not a theoretical gap. The Docker stack keeps Postgres in a named volume, and
`docker compose down -v` — the documented way to reset a stack, and the first thing anyone tries when
a container misbehaves — deletes it. The release image carries the portal and nothing else, so there
is no `pg_dump` inside to reach for either.

```bash
report-portal backup dump.jsonl          # the whole database; "-" writes to stdout
report-portal restore dump.jsonl         # dry run: validates and reports, writes nothing
report-portal restore dump.jsonl --force # replaces the database (stop the portal first)
```

**Without `--force`, `restore` is a dry run.** It reads and validates the entire file and tells you
what it would load and exactly how many existing rows it would delete. That is deliberately two
things: it makes "is this backup actually readable?" a question you can answer on a live system
without a spare database, and it means no arrangement of arguments replaces a database by accident.

**One format for both drivers**, so the runbook has one line in it whichever driver you run — and so
a dump is portable *between* them. "We outgrew SQLite" and "we want to go back to a single file" are
now a backup and a restore rather than a migration project.

**A restore is a replacement, in one transaction.** Every table in the schema is emptied, not only
the ones the dump carries, because a table the dump omits must end up empty too; anything else is a
mix of two databases that never existed. A dump cut short by an interrupted download or a full disk
leaves the target byte-identical.

`-` means stdin/stdout, so compression stays your choice. Design notes, including why this is not a
wrapper around `pg_dump`, are in [ADR 0027](../adr/0027-backup-and-restore.md).

### The hand-written reports became a set you could ask for

You could write them and read them, one at a time, wherever they happened to appear — so "what have
we written by hand this month?" meant scrolling. 浏览页的筛选栏 now has a **版本** filter.
Hand-written reports *are* a version ([ADR 0026](../adr/0026-manual-reports.md)), so the filter is the
whole answer and it generalizes for free to the internal/external forms report versions already
allow.

The options come from your data and through your own read scope: a version nobody has written in is
not offered, you are never shown the name of a version you cannot read, and naming a version you were
never granted returns nothing rather than reaching past your scope. The control does not appear while
only one written form is visible.

### The portal says at boot when `config.yaml` is readable by more than its owner

The file holds `secret_key` — which signs every session cookie and, through HKDF, unwraps the stored
SSO secrets — and during a rotation it holds the previous key beside it, so a readable config is
briefly *two* live keys on disk. The generated file is `0600`, but one copied from the example,
restored from an archive, or checked out of a repository arrives with whatever mode it had.

A warning rather than a refusal, naming the file, its mode and the exact `chmod`.

## Fixed — the process, and the operator's view of it

**A six-byte symbol could take the process down.** `marketPrefix` validated the length of a stock
code and its first byte, and nothing else; the ingest handler only trims whitespace, which does not
strip a NUL. So a code like `6\x00abc` was accepted, interpolated into a vendor URL, and handed to
`http.NewRequest` — which refuses a control character in a URL and returns a nil request. The next
line set a header on it. That ran inside a bare goroutine, and the only `recover` in this tree is in
the batch runner, so the panic ended the binary rather than the request.

**A blocked deployment looked like a healthy one.** The company-name fetch checked no status code, so
a 403 interstitial was GBK-decoded, failed the parse, and returned the empty string — the same value
a connection error returns. Two sources with no way to tell "this one refused us" from "this one had
nothing" is one source with extra steps. Both name and quote fetches now go through one client with a
context deadline, a non-2xx refusal, `io.LimitReader` on every body, and a logger capped at one line
per host per minute. That status check has a second effect: the name-table fetch reads a zero-row
page as "past the last page" and stops, so one refused page used to silently truncate the whole
company-name table.

**A restart cut every open request in half.** The portal died on `SIGTERM` the instant it arrived:
a report upsert answered with truncated JSON, an export half-written, an audit entry that may or may
not have been recorded. It now stops accepting new connections and lets in-flight requests finish, up
to 10 seconds; what is still open at the deadline is closed then. The database is closed last, after
the handlers, because closing it earlier would fail the very requests the grace period was granted
for. Background loops are deliberately not drained — a batch run interrupted by a restart is the case
[ADR 0015](../adr/0015-reconcile-not-retry-untracked.md) exists for.

**`/healthz` could not see the failure that matters.** It answered `{"ok":true}` unconditionally,
reporting only the failure an orchestrator can already see — the process being gone — and staying
green through the one it cannot: the portal up, its database unreachable. It now checks the database,
caches the verdict for a couple of seconds so probing it costs at most one `SELECT 1` per interval,
and returns a bare "unreachable" because the driver's error text can carry the DSN's host, user and
database name. It is a **readiness** signal, not a liveness one: under something that restarts
unhealthy containers, an unreachable database would become a restart loop on top of an outage.

**Cleanup deleted rows and freed no disk.** The console reported "cleaned 12,431 rows" and `df` did
not move. A pass that deleted something now reclaims and reports the bytes handed back. On SQLite
that is a gated `VACUUM` — the freelist has to be at least a tenth of the file and the file over
about 8 MiB, because the rewrite needs roughly the database's own size in temporary disk and blocks
every other query. On Postgres it does nothing, on purpose, and the console says so: `VACUUM FULL`
takes an `ACCESS EXCLUSIVE` lock on every table it touches, which is an outage of unbounded length
scheduled by a background ticker.

**API requests were not in the access log at all.** The request logger skipped `/api/` outright, with
a comment saying those endpoints have their own concise logs. They do not. A 500 on an unaudited
endpoint left no trace anywhere. The reason for the skip was real — the browser polls the home feed,
the announcements and the queue badge on a timer — so the rule that keeps both properties is to log
every API request **except a fast, successful read**: any status 400 or above, anything taking a
second or more, every mutation, and every non-API request exactly as before. Each line now carries
the client address resolved through the same trusted-proxy rules the rate limiter and the audit log
use, so an upstream you have not trusted cannot write someone else's address into your log.

**Rotating `secret_key` permanently wedged the SSO keyring.** Stored auth secrets are encrypted with
a data key, and only that data key is wrapped under `secret_key`; the comment at the top of the file
has said since ADR 0023 that rotating therefore re-wraps one row. That code was never written.
Rotating left the data key unopenable — SSO down, captcha silently failing, and no page able to
repair it, because saving a secret needs the very key that will not open. It exists now as the config
it should always have been:

```yaml
secret_key: "the new one"
secret_key_previous: "the one you rotated away from"   # or RP_SECRET_KEY_PREVIOUS
```

Restart once and delete the second line. Rotating *without* it still fails, which is correct —
minting a fresh data key would silently orphan every stored secret — but the failure now names both
ways out instead of an opaque decryption error.

**A dump overwriting an existing file kept that file's permissions.** The `0600` was passed to the
open call, where it applies only when the file is actually created, so the first nightly backup was
private and every one after it inherited whatever mode was there. A dump carries bcrypt password
hashes and API token hashes.

**A cross-generation restore was accepted, and failed a boot later.** The design said the existing
schema-baseline guard covered it. It does not and cannot: that guard runs against the database being
opened, not against the dump. The dump now records its generation in the header and a restore refuses
a mismatch before it starts.

## Fixed — work that could be lost

**Dragging a report type could bring back one you had just deleted, permanently.** The strip posts
the list the browser last read, so a type deleted since — by you in another tab, or by a colleague —
was still in it, and the save is an upsert. Reordering now writes only names that still exist; the
upsert stays where it is genuinely needed, for a *discovered* type that has no row to update.

**Dragging entry buttons could move them into a deleted group, where nothing would ever show them
again.** Same shape, worse ending: the buttons were stamped with a group id nothing resolves, hiding
them from the home page *and* the admin page at once, with no way back through the interface. A
header naming a group that no longer exists now sends its buttons to the top level.

**Three of the four drag-to-sort surfaces could not tell you a save had failed.** The admin was left
looking at the order they had just made, with the list quietly reverting on their next visit. The
server stopped discarding its own errors too: two of the three reorder endpoints looped through the
writes and answered "ok" regardless.

**The run-targets table could render an order the server does not hold** — two refetches in flight
with no ordering between their answers, and the stale winner then got written back by the next drag.
Only the newest request may update the table.

**Losing an editor draft took one click.** Closing the tab, reloading, or clicking 返回 threw it away
without a word. Both exits now ask first, where "unsaved" means a save would write something
different, not that a control was touched. Navigating away via a sidebar link is still not guarded —
that needs a router migration touching every route — and the gap is written down in ADR 0026.

## Fixed — reports saying what they are

**A hand-written correction appeared beside the workflow's own report as a second tab called
"深度分析 2".** The number was always there for a good reason — a report's identity includes its
title — but it was the wrong answer for a case that barely happened until hand-written corrections
existed. A tab that is a different written form of the same report is now named **深度分析 · 人工**,
and the number counts distinct reports rather than rows.

**A report a person wrote told nobody.** Workflow reports fired `report.ingested`; hand-written ones
fired nothing — so a downstream index or a nightly digest silently missed exactly the reports that
exist *because* the machine got it wrong. It is the **same event**, deliberately, rather than a new
`report.written`: minting a new type would leave every existing subscriber missing them until
somebody noticed. An edit that rewrote no content fires nothing, by the same rule that decides
whether a revision is filed.

**The ingest event named a version the report did not have.** The payload echoed the field the
request sent, and the store resolves an empty one to the default — so the commonest ingest announced
`version: ""` about a report stored as `"default"`. It now reports the version the row actually
carries; the audit entry for the same ingest was echoing the raw field too.

**Every ordinary report was filed under a literal "default".** The default version is seeded with no
display name and the server fell back to the internal identifier. It is named now, in the reader's
language, in both the version switcher and the new browse filter. A display name an admin actually
typed is still shown exactly as typed.

## Fixed — settings that were read and never written

Six settings had a reader, a default and a comment describing the choice an operator could make, and
nothing anywhere able to make it. A setting in that state is not configuration; it is a constant with
a misleading name.

- **Two-factor enrolments ignored your portal's name** — the authenticator label read a key nothing
  has ever written, so every entry landed under "Report Portal". It now reads the same `site_title`
  everything else does. Entries enrolled before this keep the old label until they re-enrol.
- **The run form offered twice the concurrency the server would honour.** The per-job ceiling sat at
  its built-in 10 while the picker went up to 20; choosing 15 got you 10, silently. It is on
  管理 → 运行队列 now, and the picker asks the server for its ceiling.
- **SSO could not be pointed at an IdP on your own network.** The SSRF guard refuses private
  addresses by default and its own comment calls the exception "a setting". The switch is now above
  the provider tabs, because it widens what *every* outbound SSO call may reach. Off by default,
  anything but an explicit yes reads as off, and turning it on is audited.
- **The app market could not be repointed.** The field is on 管理 → 应用, it shows the address in
  force, an empty value returns to the built-in index, and a saved address goes through the same SSRF
  guard the fetch uses.
- **Two values the server computes were on no screen at all**: whether a *running* job is actually
  running in this process (after a restart the row survives but the goroutine does not), and when a
  spent run quota comes back.
- **Six refusals reached English and Traditional Chinese admins in Simplified Chinese** — the portal
  answers with a machine-readable code precisely so the browser can translate it, and six codes had
  no string in any bundle.

## Fixed — the portal without a mouse

Fourteen controls, invisible in a screenshot, that decided whether the portal was usable at all on a
keyboard or a screen reader.

**Report cards and app cards could only be clicked** — a `<div>` with an `onClick` takes no focus,
announces as nothing, and does nothing on Enter, so there was no keyboard route into a report at all
from the page the portal opens on. **Icon-only buttons announced the picture, not the action**: a
screen reader read "key" for reset-password and "stop" for cancel-this-job, in English regardless of
the interface language. Twenty now carry a real translated name. **The page language was always
Chinese** — `<html lang>` was hard-coded to `zh`, so English text got Chinese pronunciation rules.
**Every browser tab said the same thing**, which made several tabs on one portal indistinguishable.

Then ten more that the first pass's guard did not know to look for, including one on the login page
and three that are the primary way to navigate: the captcha refresh (an `<img>` takes no focus at
all), the reader's date timeline, the review queue's open-report, compare's show-unchanged, four
places in the assistant and audit log, and the revision picker in the report edit history. The last
four are the ones a component library was supposed to have handled — antd's `Typography.Link` without
an `href` renders a focusable anchor whose Enter does nothing, which is worse than an obviously dead
control, and `List.Item` is rendered with `tabIndex=-1` so Tab cannot reach it.

None of them gained a label it did not need: an `aria-label` *replaces* the visible name rather than
adding to it, so the ones that already show their own text keep announcing exactly what they read.

**The guard is what actually changed.** It now checks every plain element carrying an `onClick`, not
the two component types the first version knew about, and a second rule covers the two antd
components the "components manage their own semantics" exemption had been waving through. Both antd
behaviours are pinned by a test that renders them, so an antd upgrade that fixes either one turns a
test red and the rule can be removed instead of outliving its reason.

## Changed

**`GET /api/v1/reports` documents the `version` field it has always returned.** Report versions
shipped in v0.4.39 and every v1 read has carried the field since; the OpenAPI schema did not list it,
so a machine consumer generating a client from the spec dropped it.

**The OpenAPI spec describes the new `/healthz`.** It is the one public endpoint the spec documents
and it had still promised a bare `{"ok": true}` and a single 200 — which would tell anyone wiring it
into an orchestrator that an unreachable database is healthy. It now documents both answers, the
two-second cache, and why a failure returns only `"unreachable"`, in all three languages.

## What it costs

Measured on SQLite with 50,000 reports carrying realistic bodies:

- **A dump takes 1.2 seconds** (~41k rows/s), and for that time nothing else writes — the dump is one
  read transaction and SQLite's pool here is one connection. A pause, not an outage, and it is what
  makes the result a snapshot instead of a table-by-table sample of a moving database. Postgres has
  no equivalent pause.
- **The file is 307 MiB uncompressed**, essentially the size of the report bodies themselves.
- **A restore takes 7.6 seconds** (~6.6k rows/s) and prints nothing until it is done. The dry run
  over the same file takes 1.7 seconds.
- **Interrupting a restore is safe**, which is the thing worth knowing during that silence. Verified
  the hard way: `SIGKILL` three seconds into a 60,000-row restore, with the file already grown to
  316 MiB and a hot journal on disk. Reopening rolled it back to exactly what was there before, and
  SQLite truncated the file back to 360 KiB along with it.

The version filter's options are a `DISTINCT` over reports on the home feed, the busiest endpoint in
the portal, so it was measured rather than assumed: **24ms at 50,000 reports** on SQLite, warm,
beside the feed's own 261ms. Left as a scan on purpose — an index on `version` would hold two or
three distinct values across the whole table.

## Not in this release

**A `/metrics` endpoint.** The obvious companion to an access log, and deliberately not added: it is
not a gap with one correct answer, it is a decision with a security posture attached. This codebase
has already taken a position that constrains it — `/healthz` exposes no counts and `/api/version` is
session-gated, both so an anonymous scanner cannot read build identity or business volume — and an
unauthenticated `/metrics` carrying report and account totals would contradict that.

**Scoring predictions against what actually happened.**
[ADR 0029](../adr/0029-prediction-scoring-deferred.md) writes the design down and states in its first
line that no code implements it. It is worth reading for two findings about code that ships today:
`SetTracking` deletes every tracking row on each re-ingest, so any machine-computed verdict is erased
by the next nightly run, and an empty tracking array is a silent no-op, so a claim that is going
wrong can be dropped without a trace. It also explains at length why there is no accuracy percentage
and why there should not be one.

## Verification

Go build, vet, gofmt and the whole `internal/app` suite, including the Postgres integration tests and
a full run under `-race`. Web typecheck, **594 tests across 85 files**, locale parity, and the SPA
build. All of it re-run on the merged tree, which is the first time the two lines of work were
compiled together.

Beyond the suites, the parts that fail silently were exercised against the built binary rather than
assumed:

- A SQLite database dumped, dry-run against an empty Postgres, restored into it, and the portal
  booted on the result — the restored account signs in with its original password and reports written
  afterwards get ids that do not collide with anything restored. Then dumped back out of Postgres and
  restored into a fresh SQLite file.
- `/healthz` answering `{"db":"ok","ok":true}` on a live Postgres, and a real `SIGTERM` producing
  "shutting down … finishing in-flight requests" followed by a clean exit.
- Three report writes and a login appearing in the access log with status, latency and caller, while
  the `/api/home` reads around them do not.
- Real quotes for Shanghai and Shenzhen codes against the live feeds, a Beijing code returning a
  price and no bars, a second request served from cache advertising the *remaining* TTL rather than a
  fresh one, every malformed symbol refused with 400, no session refused with 401 — and the exact
  six-byte NUL that used to end the process answered with 400 while `/healthz` stayed up.

The method throughout was to remove each fix and confirm a test turns red, which is also how the
weakest part of this release was found. Three adversarial reviews and a verification pass over the
quote work proved **seventeen assertions that would have passed with the code they claimed to cover
deleted** — including the nil-request check that is the crash fix above. Each is now pinned by a test
checked the same way. The same reviews caught four statements that were simply false: two code
comments and an ADR paragraph asserting that `golang.org/x/sync` is unavailable (`go.mod` carries it
indirectly; the real reason to hand-roll forty lines is that promoting an indirect dependency is
still a dependency), and a worked example naming the wrong line as where a shifted vendor response
dies. A confident false statement propagates further than a missing one.

Two source-wide scans guard rules a per-component test cannot, because the failure mode is a **new**
violation being added: the accessibility scan and the error-code translation scan. Both refuse to
pass if they match implausibly few things — a check that silently finds nothing is the failure it
exists to prevent — and both were confirmed by reintroducing a violation and watching the scan name
the exact file and line.
