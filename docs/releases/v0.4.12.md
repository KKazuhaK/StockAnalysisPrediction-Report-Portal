# v0.4.12 — SAML actually signs in, and says why when it does not

## Upgrade notes

From v0.4.3 or later — pull and restart. Two additive schema changes, applied
automatically on start: `sso_providers.icon` and `sso_providers.link_by`. Both
default to empty, which means "no icon" and "today's matching behaviour", so an
existing deployment is unchanged until you choose otherwise.

If SAML sign-in was failing for you before this release, retry it after
upgrading before changing anything at the identity provider — the failure was on
this side.

## Fixed

**SAML demanded the transient NameID it then refused.** crewjam reads an unset
`AuthnNameIDFormat` as *transient* — "to maintain library back-compat", per its
own comment — and the portal never set one. So every AuthnRequest carried
`NameIDPolicy Format="...:transient"`, a compliant identity provider obeyed, and
the portal rejected the answer because a value that changes on every sign-in
cannot key an account. A closed loop: no configuration at the identity provider
could have satisfied it.

It now sends *unspecified*, which crewjam maps to an omitted NameIDPolicy, so
the provider sends whatever its admin configured as the unique identifier — for
Entra, the claim already in the Attributes list, usually the UPN. Demanding
*persistent* would also have worked and returned an opaque pairwise id nobody
recognises. The test asserts against the serialized AuthnRequest, because the
defect was only ever visible in the bytes on the wire.

**The forgot-password form never asked for the captcha it required.** Reported
as "the toggle does nothing". The toggle was working the whole time: the server
refuses a proofless request with 400. The form never rendered a captcha, never
sent one, and caught every error to report "sent" regardless — so the switch was
enforced and invisible, and the reset mail silently never left. This is the one
form whose stated purpose is stopping an outbound-mail flood at somebody else's
inbox, and it was the one form with no gate on screen.

"Always report sent" stays, narrowed. It exists so nobody can enumerate
accounts, which is a property of failures that depend on *which* account was
named. A rejected captcha does not — the server decides it before looking
anything up — so that one refusal is shown and every other still reads as sent.

The registration form was checked for the same defect and did not have it. It is
now pinned by tests, because "already correct" is not a property that survives
on its own.

**Fetching the IdP metadata wiped the form.** The re-seed effect was keyed on the
provider object, and the page builds a fresh one on every render, so any
re-render at all re-seeded the form from the server — including the one antd
does to show a toast. The button name was what people noticed; the attribute
mappings and the enable switch went the same way. Keyed on the provider's
identity now.

**Nine SAML rejections all arrived as `bad_response`.** The login page printed a
token that named nothing, and the only real information was in a log the reader
cannot see. Each has its own reason now, and all nineteen codes the two
protocols can produce are translated. Naming them leaks nothing: every one
describes the portal's own trust configuration, never anything about the person
signing in or whether their account exists. An unrecognized code still prints
raw, so a newer server against an older page degrades to the old behaviour
rather than to an empty parenthesis.

## Added

**Choose whether an unlinked sign-in matches on username or email.** Until now
an unlinked login could only be found by the identity binding or by
`external_id`, and a collision with a local account was refused outright —
because adopting on a name the identity provider asserts hands account takeover
to anyone who can make it assert one.

That refusal is right when the portal cannot know whether the provider is
authoritative, and wrong when it is. `link_by` is how an admin says so, per
provider. Empty keeps today's behaviour and is the default: it cannot be
inferred, so it is chosen. Username and email adopt the account they name and
then write the identity binding, so every later sign-in uses the binding and
never matches on a mutable field again.

Two things it refuses rather than guesses. `users.email` has no unique index —
username is the primary key, email is a plain column — so two accounts can share
an address; an ambiguous match is an error naming the address, because choosing
would be authenticating someone as whichever row came back first. And an empty
email claim matches nothing, since falling through would let a missing attribute
adopt whichever account also has no email. Username matching folds case, like
every other username path. A disabled account is never adopted, and adoption
never creates — provisioning stays a separate decision.

**An icon on the login button.** One column holding one of exactly two shapes,
and the server refuses everything else: a built-in preset, or a path under
`/site-assets/` this portal serves itself. There is no URL field, and not for
tidiness — the login page is unauthenticated, so an image on another host would
announce every visitor to that host before anyone signs in. A `data:` URI is
refused for a second reason: inline SVG on a public page is a script vector. The
brand marks are drawn as local SVG rather than fetched. Uploads reuse the
site-asset store the site logo already uses.

## Changed

**The forgot-password form is a page at `/forgot`, not a modal.** It is the right
shape for it regardless of the ask: a form with a captcha, a failure state and a
result state has nowhere to put those inside a dialog, and registration — the
same kind of form — has been a page all along. It is also linkable now.

**The setup guide starts folded**, and "sign in with a password below" no longer
says "below": the password form is above that message, and under `sso_redirect`
it is not on screen at all until asked for.

## Verification

Go and web suites (289 web tests), vet, gofmt, both builds, and
`scripts/e2e_check.py` at 76/76.

The SAML fix and the captcha fix were both confirmed against a running portal,
not only in tests — the defects were invisible to the tests that existed, which
is how they shipped.
