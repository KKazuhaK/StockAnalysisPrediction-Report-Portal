# v0.4.37 — a session that ends says so

## Upgrade notes

From v0.4.3 or later — pull and restart. No schema changes and nothing to run by hand.

**Nothing you have configured changes.** Three numbers that were compiled into the binary are now
settings, and every one of them defaults to exactly what the constant did — a seven-day session, ten
failed sign-ins, a fifteen-minute window. The one new ceiling, on `/api/v1` requests, ships **off**:
a portal that never asked for a limit does not get one, and no integration that works today starts
getting 429s because it was upgraded.

Rolling back to v0.4.36 is clean. All four settings are `meta` scalars an older build ignores, and
it falls back to the constants it always used.

**Twenty-one new UI strings**, in all three locales.

## Fixed

**A session that ended left a blank page and said nothing.** The session can end while the page is
open — it runs out, an admin revokes it, the account is disabled — and nothing in the SPA was
listening. `AuthProvider` read `/api/me` once at boot and never again, so the app kept its idea of
who was signed in while every request underneath it came back 401. The route gate saw a user and
stayed put. Whether that showed as an error or as nothing at all was up to whichever page you
happened to be on, and there was no way back to the login form short of typing the URL.

**Worse, the app had no error boundary anywhere.** React unmounts the whole tree when a render
throws with nothing above it to catch, so a component reading a field off data that never arrived
did not produce an error page — it produced an empty one, indistinguishable from a page that never
loaded. That is the black screen, and a dead session was only one of the ways to reach it.

Both are closed. The session gate every session-backed endpoint goes through now answers with a
**code** rather than a bare 401, one subscriber in the API client acts on it, and the login form
says the session ended rather than presenting itself as though you had arrived there on purpose.
An error boundary now sits around the routes: whatever the cause, you get a card naming what
happened with a retry and a reload, which is what a blank page should have been all along.

## Added

**会话与限流, on 管理 → 登录保护.** Four settings:

- **会话有效期** — how long before signing in is needed again. Was a hard-wired seven days. An SSO
  provider's own `session_hours` still applies on top, whichever is shorter.
- **登录失败上限** and **统计窗口** — the throttle that has been protecting every login since it was
  written (ten failures per source or per account in fifteen minutes) was invisible to the person
  responsible for it. Both numbers are now visible and adjustable, and a change applies to the next
  attempt rather than at the next restart. A correct password still always passes, so the ceiling
  can never lock an account's real owner out of it.
- **API 请求上限** — new. `/api/v1` requests per minute per source, answering 429 with a
  `Retry-After` above it. **0 means no ceiling, and 0 is the default.**

## Notes

None of the four may resolve to zero — a session lifetime of zero signs everybody out and a request
ceiling of zero refuses every call, so "unset" and "forbid everything" must never be the same
number. The API ceiling is the single exception, where 0 is the real answer and the shipped one.
Throughout, a value that says nothing leaves the working one alone: out of range is refused rather
than clamped (storing one hour for an admin who typed 0 would leave them believing a policy they
never wrote), a stored value that will not parse reads as the default, and a block the request did
not carry is not a block set to zero.

The request limiter runs **before** each `/api/v1` handler's own token check. A ceiling that only
applied to authenticated callers would leave the unauthenticated flood — the one worth shedding — to
do its work first. It counts by source address rather than by presented token for the same reason:
a token nobody has validated yet is a string an attacker picks, and keying on it would hand out a
fresh budget per made-up token. Each source gets its own counter, so one busy integration cannot
spend everybody else's allowance. It is a fixed window, which can pass up to twice the ceiling
across a boundary — the accepted cost of a counter whose job is to stop a runaway integration
rather than to meter a paid API.

Distinguishing which 401s mean "your session is gone" is the whole of the fix, and it is done by the
server's code, not by the status. A wrong password at the login form and a failed step-up are 401s
too; acting on those would end a session the user still has, mid-task.

**Not implemented, deliberately: JWT issuer and refresh-token lifetime.** A portal session is an
HMAC-signed cookie, not a JWT — there is no issuer and there are no refresh tokens, so those two
fields would be settings nothing reads.

## Verification

Go build, vet, gofmt and the full Go suite; `govulncheck` reports 0 reachable findings. Web
typecheck, 447 tests across 71 files, and the SPA build. Thirteen new Go tests and fourteen new web
tests: that every limit defaults to the shipped behaviour, round-trips, survives a save that does
not mention it, is refused rather than stored when it is nonsense, and reads as the default when
what is stored will not parse; that the configured lifetime reaches the signed token and not only
the cookie's MaxAge; that the login ceiling and window are the ones in force; that the API ceiling
is off until set, refuses above it without reaching the handler, and counts each source separately;
that the session-gone signal fires for the session code and for nothing else — not a wrong password,
not a bare 401, not a 403 — and still throws so the caller is not left waiting; that the provider
acts on it and does not claim a session expired for somebody who never had one; and that the error
boundary shows a page, carries the message, and can be retried.
