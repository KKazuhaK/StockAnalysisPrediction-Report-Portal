# v0.4.9 — an audit log, and quotas that fit the billing cycle

## Upgrade notes

From v0.4.3 or later — pull and restart. Three additive schema changes, applied
automatically on start: the `audit_log` table with its indexes,
`user_groups.run_quota_period`, and `cleanup_runs.audit_deleted`. Nothing needs
re-entering and nothing is rewritten; a NULL period means per-day, which is what
every existing row already meant, and an old history row reads as zero audit
rows deleted, which is what it was.

Rolling back to v0.4.8 works — all three additions are new, so the older
binary simply ignores them — with one thing to know. `run_quota_period` is a column
v0.4.8 cannot see, so an OU quota edited *during* a rollback window keeps
whichever period was set before it: change a cap to 9 in the old UI on a group
that was on "per month", come back to v0.4.9, and it is 9 per month, not the 9
per day the old UI meant. If you roll back, re-check any OU quota you edited.
Verified by actually running it: v0.4.8 → v0.4.9 → v0.4.8 → v0.4.9 against one
SQLite file, with writes at each step.

## Added

**A log of who read what, and who changed access.** The portal serves people
outside the company now, and "only your OU can see this" has been an assurance
rather than something the portal could evidence. This is the evidence.

One table for two audiences, because they are the same shape — actor, action,
target, when. "Who read this report" is what a client asks; "who changed this
grant" is what an operator asks when something is visible that should not be.
Two tables would mean a UNION for the one query that matters, the time feed.

Reads are recorded at `loadRep`, the single point every path serving a body to
a person already goes through — the stock page, the run page, the day export,
the Markdown and PDF exports, the version switcher. Recording there rather than
in each of them is what makes the answer complete, and stops a path added later
from silently escaping the log. Successful reads only: a refusal is a different
question, and logging it here would fill the table from any stale link.

Grant changes carry both sides. The current state answers "who can read this
now"; only the log answers "when did they gain it, and who granted it".

Two decisions are for the OU-scoped permission work coming next. `actor_ou` is
stamped at write time rather than resolved later — people move between OUs, so
a join against `users.group_id` would answer "which OU are they in now", which
is not what an audit line means; narrowing the view to one OU later is a WHERE
clause rather than a migration. And the endpoint is gated on
`requirePermJSON(PermManage)`, not on `role == "admin"`, so granting it to an
OU-scoped role becomes a registry entry.

`WriteAudit` never returns an error. An audit write must not be able to fail
the operation it describes — a portal that refuses to serve a report because it
could not log the read has turned observability into an outage.

The console is under Manage → System, and retention is the storage console's
fourth target, next to the other three rather than in a settings page of its
own. Off means keep forever, and off is the shipped default. The floor when it
is on is 30 days rather than the year reports get: an operator who wants a
short trail should have one, and the protection that matters for an audit log
is the other one — that nothing is deleted until somebody chooses it.

Two things a row needs to be readable without cross-referencing anything else.
An OU id means nothing on screen, so ids are resolved to names once server-side
rather than per row in the client — and it is the OU the actor was in at the
time, which is the whole reason that column is stored. A machine caller has no
username, so the cell says "(API token)": an empty one reads as a bug rather
than a fact. The action filter is built from the values present in the data, so
rows written by an older build still filter correctly.

**A run cap over a day, a week, a month, or a lifetime.** The cap was
runs-per-day and nothing else, which does not match how the limits are actually
sold — a client on a monthly retainer, a trial with a fixed total.

One nullable column, resolved down the OU tree like every other governance
field, and NULL means day: that is what every row written before it meant, so
an existing deployment keeps its behaviour with no backfill. An unrecognized
value also means day, which is both the prior behaviour and the narrowest
window — a hand-edited row can never accidentally widen an allowance.

The period is stored and inherited with the number, never separately. Resolving
them apart would let a cap of "20" from one OU meet a period of "month" from
another and produce a limit neither of them configured.

Almost all of the counting was already there: `RunsToday` took a "since", so
the change is which instant that is. `total` has no since at all — it is the
life of the account, and it keeps the account-instance floor, so a lifetime cap
does not count runs made by a previous holder of the username. Boundaries are
computed in the panel timezone, like the daily one already was: a quota that
resets at the server's midnight rather than the business's is wrong for exactly
the people it governs. Weeks start Monday, and the test for that is not
decoration — Go numbers Sunday 0, so the obvious subtraction puts the week
start six days in the future on a Sunday.

**An SSO setup guide that says which of the IdP's boxes each value goes in.**
The SSO page already showed every value an admin has to copy — SP Entity ID,
ACS URL, redirect URL, all read-only and all correct. What it never said is
where they go. Looking at Entra's SAML blade you see "Identifier (Entity ID)"
and "Reply URL (Assertion Consumer Service URL)" and have to guess which portal
value belongs in which, and the guess is not obvious: both are https URLs under
the same path prefix, and one of them is called neither of those things here.

So the guide is not prose about SAML. It is a table pairing each value with the
name of the box, and a vendor picker that changes only those names — Entra's
"Reply URL" is Okta's "Single sign-on URL" and Keycloak's "Valid redirect
URIs". The values are properties of this portal and never move. Product names
and protocol terms stay untranslated on purpose: an admin matches them against
what is literally printed on the IdP's screen.

It also says the thing that saves the most time and is invisible from here: the
Entity ID is itself the SP metadata document, so Entra's "Upload metadata file"
takes that URL and fills both boxes at once. Nothing is stored — the picker is
documentation, not a claim about which IdP is in use — and it folds itself away
once the provider is enabled and answering.

## Changed

**The runnable-workflow allow-list is a matrix.** Three things were wrong with
the list of expanding rows, and you could see all of them in one screenshot.

A `Tag.CheckableTag` looks nearly the same checked as unchecked, so the four
surface toggles read as four identical buttons and the state was unreadable.
They are checkboxes now. The surfaces only appeared once the workflow was
switched on, so you could not see what a workflow would offer without enabling
it; they are always visible, disabled while it is off. And a vertical list
cannot answer the question an admin actually has — "who may use 批量?" —
because that means reading down a column that did not exist. It is a table with
a column per surface now, and each column header carries a toggle-all, which
with a dozen workflows turns twelve clicks into one.

A surface the target itself does not permit renders as "—" rather than as an
unchecked box you may tick and which would silently do nothing.

## Fixed

**The run form said "today" regardless of the window.** The chip read "N of M
runs left today" from a single string. With a monthly or lifetime cap that
sentence is simply false, and false in the direction that matters — it tells
someone they get a fresh allowance tomorrow when they do not.

**The quota refusal printed a machine token.** The 429 put `rate_limited` in
the `error` field, which is the field the toast prints, so an external user who
ran out of runs was shown that string. The token moved to `code`, where every
other handler puts it, and `error` carries a sentence.

**The OU panel offered "inherit — unlimited" under a capped parent.** The panel
resolved the quota the way it resolves urgent policy and max-queued: a flat
fallback to the Default group. But the quota is tenancy, and tenancy inherits
down the OU tree — `EffectiveGroupSettings` walks root → primary group and
takes the deepest non-NULL. So an OU under a parent capped at 20/month was told
that choosing inherit would remove the cap, when it would have applied one. The
panel now walks the same chain the server does, cycle-guarded, and reports the
period from the same ancestor as the number.

**What the pre-release review found**, all of it in code written this cycle.

The biggest was in the quota resolution, and it only appears on an upgraded
database. `EffectiveGroupSettings` replaced the inherited *number* whenever an
OU set one, but replaced the *period* only when that same OU also had a period
stored — and after an upgrade no OU has one, because the column is added empty
and nothing is backfilled. So a child OU capped at 5 (written by an older
build) kept its 5 while inheriting an ancestor's newly-set "month": 5 runs a
month where it had been 5 a day, thirty times tighter than anyone chose, and
invisible because the console reads the same NULL as "day". The window is now
replaced whenever the number is, defaulting to day — which is what the SPA
already did, and why display and enforcement had diverged rather than both
being wrong.

The comparison view read both report bodies without going through `loadRep`, so
it wrote no audit line. That is a real hole rather than a technicality: the diff
returns the full text of every non-identical section of *both* documents, and
side B is normally one the reader never opened — exactly the read a client asks
about. Both sides are now recorded through the same writer.

The audit console's "clean now" confirmation read its count out of the tokens
field, so a purge of the one category that cannot be regenerated was confirmed
with "permanently delete 0". And the allow-list matrix's column header computed
its checked state over every workflow while acting on only the enabled ones, so
one workflow switched off left the header permanently unchecked — it could
grant a surface across the board and never revoke one.

Three smaller ones. A version's audit line now records the visibility change as
well as the grants — reading a version needs both, so recording only one made a
visibility flip log as "before == after" — and it is written after the change
lands rather than before, because a line asserting an access change that then
failed is worse than no line at all. The cleanup history had nowhere to put the
audit count, so a pass that deleted 900 audit rows was remembered as having
deleted nothing; `cleanup_runs` gained the fourth column its three siblings
already had. And the post-cleanup toast now names the audit count too.

## Removed

**`/api/repbody`** — an SPA endpoint the SPA never called. The stock page loads
a report by symbol+date, the version switcher by `/api/report/{id}/versions`,
and nothing anywhere asked for a body by bare id except `e2e_check.py`. The
check it backed was nearly a duplicate of the line below it, which already
fetched `/report/{id}/md` and asserted only the status code; that one now
asserts the content instead, so the suite went from two weak checks over two
paths to one strong check over the path the product actually serves a body
through.

## Verification

Go and web suites (276 web tests), vet, staticcheck, gofmt, both builds, the
Postgres integration tests, and `scripts/e2e_check.py` at 76/76 — with the log
filling itself along the way, 4 report reads and 5 grant changes recorded, none
of which the script asks for.

The upgrade and the rollback were run rather than reasoned about: two binaries,
one SQLite file taken v0.4.8 → v0.4.9 → v0.4.8 → v0.4.9, every step serving
`/healthz` with no error in its log, and the schema diffed at each end. The
only differences are the two new columns and the new table with its three
indexes.

Also raised vitest's per-test timeout, the other half of a fix only half made
earlier. Raising testing-library's async budget stopped assertions reporting a
pre-update value, but each test still had vitest's own 5s ceiling, and under a
contended pool a whole test can legitimately exceed it — reported as "Test
timed out" rather than as a wrong answer. The failures kept roaming between
files, which is the signature.
