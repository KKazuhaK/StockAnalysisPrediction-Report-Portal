# v0.4.29 — a slow link stops being told things that are not true

## Upgrade notes

From v0.4.3 or later — pull and restart. No schema changes and nothing to run by hand. Rolling back
to v0.4.28 is clean; everything here is client behaviour plus one response header.

**Every response under `/api/` and `/report/` now carries `Cache-Control: no-store`.** If anything
in front of this portal was caching those — a reverse proxy with `proxy_cache` on, a CDN rule — it
will stop. That is the intent: those responses are per-user. Static assets are unaffected and keep
their existing caching.

## Fixed

**The run dialog claimed there was nothing to run while it was still asking.** On a slow link,
clicking Run analysis opened an empty workflow picker under a notice reading "no workflows are
configured". That notice is a statement about the server, made before the server had answered, and
the OK button was live throughout. The dialog now waits — visibly — for the two answers it cannot
be honest without: the workflow list and the run-form defaults. The three secondary calls (urgent
tickets, run quota, queue depth) stay outside the gate; they add detail to controls that read
correctly without them.

**Four settings pages presented their own defaults as your configuration.** The run-queue, mail,
storage-cleanup and login-protection pages rendered the moment they mounted, filled with whatever
their fields start at — one job at a time, mail off on port 587, cleanup disabled — and replaced
them when the server answered. On a fast link that is a flicker. It was worse than a flicker twice
over: the form is live from the first frame, so an admin on a slow link could read a value the
server never sent and save it back (the run-queue page posts every field it holds), and a load that
failed outright left those defaults on screen for good, because none of these loads had a `catch`.

They now show a spinner until their own request lands, and if it fails, what went wrong and a retry
— never the fields. Login protection previously rendered nothing at all, so a slow load looked like
a page with no settings on it.

**A chart's SVG was uploaded on every render, not once.** Charts re-render on every mount, so
paging into a report, out, and back in re-sent byte-identical payloads — up to a megabyte each, and
a report can carry several. The upload is now remembered per tab, keyed by source, theme and
renderer version, and recorded only once the server has taken it, so a failed upload is still
retried.

**Two background refreshes ran in tabs nobody was looking at.** The site-settings poll checked
visibility only in its visibilitychange handler and not in its interval, so a tab left open behind
others asked every 60 seconds indefinitely. The home feed listened for both `focus` and
`visibilitychange` — which both fire on a tab switch — with no in-flight guard, so returning to the
tab sent two identical requests and a slow answer could be overtaken by the next tick. Both now go
through the shared visibility-aware poller.

## Added

**Warming what the next click needs, while the shell is idle.** The portal fetches on open, so the
first second of a dialog or a settings page was spent waiting even though the shell had been idle
beforehand. `lib/prefetch` moves that work into the idle time under three rules that keep it a head
start rather than a second, quietly-wrong source of truth: a warm answer has a maximum age the
reader states, the reader still issues its own request and overwrites it, and nothing is warmed on
a connection the user asked us not to spend or for a hidden tab. Failures are not cached.

Two places use it. The shell warms the run dialog's two gating answers a second after mount, only
for a user who can actually run one. And hovering a settings page in the admin rail warms that
page's own configuration — one request for the one page about to be opened, rather than warming an
admin area most sessions never visit.

The hover table lists only the cheap, page-defining GET. Storage warms its schedule and not the
usage call, which measures the database; the apps page is absent entirely, because its list comes
from a remote market with a 25-second timeout. A hover must not be able to start work like that.

## Changed

**API and export responses say outright that they must not be stored.** Everything under `/api/`
and `/report/` is answered against a session cookie and specific to that user, and none of it
carried a `Cache-Control` header at all. A response with no `Cache-Control` is not one that nothing
will cache — it is one where the decision is left to whoever is in the path. The portal is
self-hosted, so what that path contains is not ours to assume. Handlers with their own considered
answer still override it: the SSE stream keeps `no-cache`, hashed assets stay immutable, site
assets keep their five minutes.

**The report-chunk preload stands down on a metered or 2G connection.** The shell preloads the
report pages a second after mount, which is a bet that the visit will open a report — a bet a visit
that only goes to the admin console never pays off. Where the browser says outright that the bet is a bad one
(Save-Data, or a 2G connection), those chunks stay lazy.

## Verification

Go build, vet and gofmt; the Go suite; web typecheck, 352 web tests and the SPA build.

The two SSRF pre-check tests noted in v0.4.25 still fail on a machine whose resolver answers every
name — they assert that an *unresolvable* host is not rejected at save time, so they need a resolver
that can still say no such host. Unrelated to this release and green on CI.
