# v0.4.49 — the portal without a mouse

## Upgrade notes

From v0.4.48 — pull and restart. No schema changes, no configuration, no API changes.

## Fixed

Four things that are invisible in a screenshot and decide whether the portal is usable at all for
someone on a keyboard or a screen reader.

### Report cards and app cards could only be clicked

They are the primary way into a report and into an app, and both were a `<div>` with an `onClick`.
A `<div>` takes no focus, so Tab walks straight past it; it has no role, so a screen reader does not
announce it as anything you can do; and Enter does nothing. There was no keyboard route into a
report at all, from the page the portal opens on.

They are now real controls: focusable, announced as buttons, named by the report or app they open,
and activated by Enter or Space as well as by a click. A control *inside* a card — a button, a link
— still handles its own keys without the card opening behind it.

### Icon-only buttons announced the picture, not the action

A button with only an icon inherits its name from the icon itself, so a screen reader read out
"edit", "delete", "key", "stop" — the glyph's English name, in English regardless of the interface
language, and in two of those cases not the action at all. "Key" is how you reset a user's password;
"stop" is how you cancel a queued job.

Twenty of them now carry a real name, translated with the rest of the UI: delete, edit, reset
password, cancel this job, remove this row.

### The page language was always Chinese

`<html lang>` was hard-coded to `zh` and never changed. Switch the interface to English and a screen
reader still applies Chinese pronunciation rules to every English word, which is not an accent — it
is unintelligible. It now follows the active UI language, and the static default is the more precise
`zh-CN`.

### Every browser tab said the same thing

The title was the site name and nothing else, on every page. With several tabs open on one portal —
which is how one report gets compared against another, or a run watched while an admin page is
edited — they were indistinguishable, and browser history was a column of identical entries.

The tab now names the page, with the site name after it: *Queue · 智研平台*. A reader page is named
by what it is showing, since that is the only thing that tells two open reports apart. The home page
and the signed-out pages keep the bare site name, and the labels come from the same i18n keys the
navigation uses — so a page renamed in the menu is renamed in the tab, in the reader's language.

## Verification

Web typecheck, 81 files / 543 tests, locale parity, and the SPA build. Go build, vet, gofmt and the
full Go suite (unchanged this release, run to confirm it).

The keyboard-activation helper is tested for all four of its properties separately — reachable,
announced, named, and activated by Enter *and* Space — plus that other keys do nothing and that a
control inside a card is not shadowed by it.

The two source-wide rules are guarded by a scan rather than by a test per component, because the
failure mode is a **new** violation being added and a per-component test cannot fail for a component
that does not exist yet. Both were confirmed by reintroducing a violation and watching the scan name
the exact file and line. The scan additionally refuses to pass if it matches implausibly few
components: a check that silently finds nothing is the failure it exists to prevent.

The route list is read out of the router itself and every route is required to have a title —
a check that found one the first table missed (an installed app's page, which fell back to the bare
site name and so looked identical to home). It now says the section, which is the most that can
truthfully be said there: an app's own name is not available at that level, the same limitation the
breadcrumb has. A route added later cannot silently go unnamed, and the scan refuses to pass if it
matches implausibly few routes.

The tab title is tested as a table — every static route, the reader pages, an unknown manage tab
falling back to its section rather than going blank, a trailing slash, and a malformed percent-escape
in a hand-typed URL (which must not throw; a title is never worth an exception).
