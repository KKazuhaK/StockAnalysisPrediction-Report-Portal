# v0.4.49 — pick your own dates

## Upgrade notes

From v0.4.48 — pull and restart. No schema change, no migration, no new setting, and no new vendor
host: the window comes from the *same* `fqkline` endpoint the daily ranges already use, with its two
date slots filled instead of left empty.

Rolling back to v0.4.48 removes the picker. A link carrying `from=`/`to=` opens on the older build as
the default 近3月 rather than as an error.

## New

**近3月 is no longer one of only six answers.** The quotes app has a date picker beside the range
strip: choose any start and end and the chart draws the sessions in that window. Measured on the
vendor rather than assembled from a bar count — `2026-03-02 → 2026-04-10` asks Tencent for exactly
that span and gets back the 29 sessions Shanghai traded in it, and the 27 Hong Kong did. The count is
what the market actually opened, not a number this portal picked.

**A window replaces the range rather than narrowing it.** Picking dates clears the preset; clicking a
preset clears the dates. The URL carries one or the other, so a link you paste into a chat reopens
showing the thing you were looking at — a link holding both would reopen as whichever half its reader
honoured.

**A source that cannot take dates is skipped, not asked.** Sina's endpoint takes a bar count and
nothing else, so it does not declare the window and never sees one. Had it been asked anyway, it
would have answered the last N sessions **under your chosen dates** — a chart that is wrong in the
one way a chart must never be. Tencent declares it; on a deployment where nothing enabled does, a
windowed request degrades to the price with the empty-chart notice v0.4.48 added, which says the
window has no source rather than blaming the market.

**A malformed window is refused with a reason, not quietly turned into something else.** Both dates
or neither; `YYYY-MM-DD` only; start no later than end; and a span ceiling. A half-open window is a
400 rather than a guess about which end you meant, and a bad one never reaches a vendor — the
alternative is the default window drawn under your own dates, which looks like an answer.

The picker will not offer a date after today.

## Known: 分时 for a chosen past day is still not possible

The ask that started this line of work was "某天的更细精度" — one chosen day, minute by minute. The
daily window is the half that could be built. The other half cannot, and the reason is measured:
Tencent's two intraday endpoints **ignore every date parameter** — `minute/query?date=20260901`
answers with *today*, and `day/query?days=30` answers with the same last five sessions as always.
Yahoo's `period1`/`period2` would express it, but this endpoint answers **429** from the environment
this was built in, and a parser here is written against a committed measurement rather than a guess.

## Verification

Go build, vet, gofmt and the whole `internal/app` suite including under `-race`. Web typecheck, the
full vitest suite, locale parity across all three bundles and the SPA build. No new dependency in
`go.mod` or `web/package.json`, and no new vendor host.

Both captured bodies are committed beside the tests, and the existing parser and drift gate read them
unchanged — the bounded response is the same `day` array and the same 88/78-field snapshot the
count-based form sends, which is why no second parser exists.

Eight mutations were applied and reverted. **Two survived and are now covered**: the cache key, whose
test was pointed at the wrong file the first time; and the rule that a link never carries both a
window and a range, which no gesture in the page's test suite could reach because the only path to it
is antd's RangePicker. That one is now a pure exported function with its own tests, which is a better
place for a claim about what a link contains than a control that is hard to drive.

`quoteParseWindow` is asserted against eleven refusals, including the two that would reach a vendor
URL as something other than a date.
