# v0.4.13 — the SSO page tells you which claim to map

## Upgrade notes

From v0.4.3 or later — pull and restart. No schema change, nothing to
re-enter.

If SAML sign-in refused you with "no account for this identity" while the
account plainly existed, retry after upgrading before changing anything. Both
causes were on this side.

## Fixed

**An email-format NameID is the email, so it is matched on.** With
`link_by = email` and the email claim left unmapped, a sign-in whose NameID was
`someone@example.com` was refused with "the assertion carried no email to match
an account with" — while the address sat in the subject of the very assertion
being refused.

Entra sends the configured unique identifier as the subject, which for a normal
tenant is the UPN, which is an address; since v0.4.12 stopped demanding a
transient NameID, that is exactly what arrives. And the sibling branch has
always worked this way — username matching falls back to the subject when its
claim is unmapped — so email matching not doing the same was an inconsistency,
not a safeguard.

It is guarded on the shape, so an opaque subject cannot silently become an
address: one `@`, something either side, a dot in the domain, no spaces. Not
validation — the lookup that follows is an exact match against a stored address,
so being slightly permissive costs a miss, never a wrong match. A mapped claim
still wins; the fallback is only for the unmapped case.

**"No account for this identity" was blaming the wrong setting.** Every refusal
during account resolution collapsed into one code whose message asserts a
specific cause — that this provider does not create accounts — which is one of
several and, in the reported case, not the real one. The account had never been
looked up: the email claim was unmapped, so matching refused before touching the
user table.

Splitting it costs nothing. Every refusal that depends on *which* account was
named stays one indistinguishable answer, because telling those apart makes the
login page a user-enumeration oracle against the identity provider — including
the ambiguous-email case, which would otherwise reveal that two accounts share
an address. "This provider has no email claim mapped" depends on no account at
all: it is decided before any lookup. And the generic message no longer names a
cause; it says the log has the reason.

## Added

**The claim names the identity provider actually sent, on the SSO page.** Every
field in the attribute-mapping section is a claim *name*, and providers disagree
about them — Entra and ADFS send long URN forms, Okta and Keycloak short ones. A
wrong guess fails the sign-in with a message about accounts, which points
nowhere near the blank field that caused it.

The endpoint that answers this shipped with SSO and nothing ever called it. Its
own comment says attribute mapping is otherwise configured by guesswork and that
showing the real keys turns it into a glance — and the guesswork it was written
to end went on, and cost a real sign-in. That is a whole feature reachable only
by `curl`.

It renders above the mapping fields now, each name copyable, with the last value
beside it so you can tell which is which. When nothing has signed in yet it says
so, and says that even a *failed* attempt records the names — which is the state
an admin is in the first time they need it.

## Verification

Go and web suites (291 web tests), vet, gofmt, both builds, and
`scripts/e2e_check.py`.

The reported case was reproduced against a real store before and after the fix —
an existing account, an email-format NameID, no email claim mapped — and the
assertions are that the *existing* account is adopted, that no second one is
created, and that the identity binding is written so no later sign-in matches on
a mutable field again.
