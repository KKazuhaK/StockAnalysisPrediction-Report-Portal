# v0.4.18 — the audit log records visitors, not your reverse proxy

## Upgrade notes

From v0.4.3 or later — pull and restart. No schema change.

**One behaviour change worth reading.** An unset `trusted_proxies` used to mean
"trust nobody"; it now means "trust loopback". If your portal is reached
*directly* and you were relying on the old meaning, set `trusted_proxies:
["none"]`.

If you run behind a proxy that is **not** on loopback — Docker's bridge gateway,
another host — it still has to be named, and the portal now tells you so instead
of silently recording the proxy's address:

```yaml
trusted_proxies:
  - "172.16.0.0/12"   # Docker's default bridge range
```

## Fixed

**Every audit row recorded the reverse proxy's address.** Reported from a live
portal showing `172.20.0.1` — a Docker bridge gateway — for every visitor.

`clientIP` was not the bug. Refusing to believe `X-Forwarded-For` from a peer that
is not in `trusted_proxies` is what stops any visitor claiming any address, and a
column full of self-declared addresses would be worse than no column at all. The
bug is that the portal *knew* and said nothing: a request carrying that header
from an untrusted peer is precisely "there is a proxy in front of me and nobody
told me to trust it", and the result was a table full of a plausible-looking
address, identical for everyone. **A wrong address that looks like data is worse
than a blank one.**

It notices now, and the audit page says so in a warning that names the exact fix.
Louder than the IP-database footnote beside it, because this one means the column
is actively misleading rather than merely empty.

**And the default was the wrong one.** An empty list meant "trust nobody", so a
portal behind nginx or Caddy *on the same host* — the ordinary deployment —
recorded the proxy for every visitor while looking like it worked, and fed the
same wrong address to the per-IP rate limiter. Unset means loopback now, which
makes that deployment correct with no configuration and cannot be exploited by
anyone who is not already on the host.

Two tokens come with it, matching the sibling panel, because the useful policies
are not all a list of networks:

- `all` / `*` — trust every upstream. Correct behind a listener nothing but the
  proxy can reach (a Docker network, a unix socket) and a hole anywhere else, so
  the server logs a warning at boot: it is right exactly once, and an operator who
  set it for a Docker network and later published the port has nothing else to
  remind them.
- `none` — trust nobody, not even loopback. The previous behaviour, still
  available for a portal that really is reached directly.

Neither combines with a list of networks. A list plus a token is a contradiction,
and quietly picking one reading would hand an operator a trust policy they did not
write.

`config.example.yaml` documents all four cases, since that is where an operator
looks before they look at a warning.

## Verification

Go and web suites (302 web tests), vet, gofmt, both builds, and
`scripts/e2e_check.py`.

Both ends verified against a running portal from clean starts: with the proxy
untrusted the peer's address is recorded and the hint is raised; with it trusted
the visitor's address is recorded and the hint is gone.

Addresses recorded before this upgrade are left as they are. They faithfully
record what the portal could establish at the time.
