# v0.4.4 — login modes, an OU tree, and the audit that followed

Two features, and then fifteen defects an adversarial review of them found —
most of which were in the features themselves.

## Upgrade notes

From v0.3.10 — one step, unchanged from v0.4.3. Back up first.

From v0.4.1 — the portal now REFUSES to start instead of booting into silent
damage. Its adoption steps went in v0.4.3, so the keyring would be read from
`meta`, missed, and a second data key minted: every secret sealed under the
first becomes undecryptable at runtime with no error, and the SSO group rules
read as empty, re-placing every federated user into their provider's default
OU. Recreate the database, or run v0.4.2 once to migrate it first.

Schema: no change. users.created_at is now populated — it was a declared
column nobody ever wrote.

## Added

Four login modes on two axes. login_mode (dual / sso_first / sso_redirect /
local_only) decides what the sign-in page OFFERS; sso_only decides what the
endpoint ACCEPTS. A mode alone would be decoration, since anyone can POST to
/api/login whatever the page drew. Both fail safe with no provider enabled,
admins are always exempt from sso_only, and enabling it is refused outright
unless an admin with a LOCAL password exists to fall back on — a federated
admin is nilled out before bcrypt and never reaches the exemption at all.

An organizational-unit tree beside the account list, after the Google
Workspace admin console: collapsible, searchable, all-vs-selected scoping,
single/multi select. OUs have been a tree since ADR 0022 and every screen drew
them flat, which is why inheritance was impossible to reason about. Selecting
an OU includes its descendants, because a setting on a parent already governs
the subtree. No data model change.

## Fixed — the review

A session outlived the ACCOUNT. session_rev restarted at zero on a recreated
row, so a deleted user's still-valid cookie authenticated them as whoever took
the username next, with its OU, role and reports. New accounts now start at a
revision nobody has held.

The break-glass path did not escape. ?local=1 skipped the redirect without
revealing the password form, leaving the operator on a page whose only control
was the provider that had just failed. And sso_redirect plus any SSO failure
was an unbreakable loop — browsers break server-side redirect chains, not
JS-driven ones. Both closed, and the page now says why the handshake failed.

local_only + sso_only locked out every non-admin: the inertness check asked
whether a provider was enabled, not whether the page offers one.

sso_only was enforced only at the login form, so a user online when it was
switched on could renew a full session indefinitely via a password change.

A deleted account's queued jobs were still dispatched to Dify and billed, and
its run counters carried over to the next holder of the name. The delete is
now one transaction with the users row removed first, so nothing can
re-create a swept row behind it.

Self-registration was the last creation path still comparing usernames
case-sensitively. And the case guard folded with SQL LOWER(), which is
ASCII-only on SQLite — 'ÉLODIE' and 'élodie' became two accounts sharing one
read principal. Both fold in Go now, the way userPrincipal does.

The OU tree's member count showed direct members while the click listed the
subtree; searching remounted the tree and destroyed the admin's expansion;
deleting the scoped OU left the list silently empty; and force-SSO redirected
visitors who already held a session.

Toasts came out white on dark pages — antd's static `message` renders outside
ConfigProvider. A guard test now forbids the static APIs entirely.

A real flake in the web suite, about one run in eight: testing-library's 1s
async budget is a bet on scheduling, and a provider whose fetch had not
resolved still showed its pre-fetch fallback. Confirmed pre-existing by
running with and without the new tests.

## Verification

Go and web suites (227 web tests, ten consecutive clean runs), vet,
staticcheck, gofmt, both builds, the Postgres integration tests, and
scripts/e2e_check.py at 77/77 against a real running portal.
