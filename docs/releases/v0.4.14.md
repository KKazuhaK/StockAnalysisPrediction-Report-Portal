# v0.4.14 — the account list shows activity, not just sign-ins

## Upgrade notes

From v0.4.3 or later — pull and restart. One additive schema change applied
automatically on start: `users.last_seen`. Existing rows read as empty, so
every account shows no activity until its next request; the column fills itself
within minutes of people using the portal.

## Changed

**The account list's last column is activity now, not the last sign-in.**
"Signed in on Monday and used the portal all week" and "signed in on Monday and
never came back" are the two answers that column gets consulted to tell apart,
and showing the login time made them identical.

Renaming the heading alone would have made it lie, so the data changed with it.
The stamp is recorded in the session middleware, which every authenticated call
already passes through — recording it there rather than in handlers is what
makes "activity" mean all of them, instead of a list somebody has to remember to
extend.

It is throttled to one write per account per five minutes. A write per request
would be a row update per page load per user, and five minutes is far finer than
the question the column answers. The throttle lives in memory, so a restart lets
each account's first request through, which is correct rather than merely
tolerable: that request *is* activity.

The sign-in time is kept rather than repurposed — it is what you want when you
are looking at a sign-in you did not expect — and is the tooltip on the cell.

## Fixed

**The "back to sign in" link stopped hugging the button above it.** On both the
reset-password and the registration form it sat directly under the primary
action's edge with no gap. A link touching the button it undoes is a misclick
waiting to happen, and on the reset form that misclick throws away a captcha the
person has just finished typing.

## Verification

Go and web suites (291 web tests), vet, gofmt, both builds, and
`scripts/e2e_check.py`.

The activity stamp was exercised against a database written by v0.4.13 and
reopened by this build, so the column added in place is the one being written —
assumed of an `ALTER`, verified here.
