# v0.4.23 — exported reports print in a font somebody chose

## Upgrade notes

From v0.4.3 or later — pull and restart. No schema changes, nothing to run by hand, and rolling
back to v0.4.22 is clean: everything here lives in the image and in how a PDF is drawn, not in
your data.

**Exported PDFs will not be byte-identical to the ones you have already downloaded.** The body
font changes, so line breaks and page boundaries shift slightly. No content is added or lost, but
a report exported before and after this release will not diff page-for-page.

**If you build the image yourself**, the build now fetches the font from
`raw.githubusercontent.com` at a pinned upstream tag and verifies its SHA-256. A build host with
no route there will fail at that step rather than silently produce an image with no CJK font.

## Fixed

**Every exported PDF was drawn in whichever font the container happened to have.** Exports are
rendered by wkhtmltopdf inside the release image, so the stylesheet's font stack resolves against
that image's fonts — not the reader's machine. The stack named three families and only one of them
was ever installed: Noto Sans CJK SC had been dropped from the image to keep it small, and
Microsoft YaHei is a proprietary Windows font that cannot ship in a container at all. So every
report fell through to the third choice by accident rather than by decision.

The font it landed on draws thin, unevenly weighted strokes and does not compress CJK punctuation
— a full-width gap sits before every comma — which is what made exports look washed out and
slightly wrong without it being obvious why.

The image now installs a single weight of Noto Sans CJK SC, pulled from the pinned upstream tag
and checksum-verified. It covers the full CJK range and is OFL-licensed, so unlike the font people
usually reach for here, it can actually be redistributed. At ~16 MB against the ~15 MB package it
replaces, the image stays the size it was.

**Chart labels came out in a different face than the text around them.** The same mismatch from
the other side: the browser inlines the `font-family` it computed locally into the chart SVG it
uploads, so a reader on Windows sent `Microsoft YaHei` — a name the render container cannot
resolve. The chart then fell back to something other than the body font, in the middle of a page
set in the body font.

Chart fonts are now pinned to the container's font while the SVG is sanitized, which is the
boundary that already exists and the one place a client value cannot slip past.

## Changed

**The browser-print fallback and the server template now describe the same typography.** When
wkhtmltopdf is unavailable the portal prints through the browser instead, and that path had drifted
to a different font stack and font size. It still names local fonts the container does not have —
that path runs on the reader's own machine, where naming them is correct — but it now leads with
the same font the server uses, so the two exports agree wherever both can.

## Verification

Go and web suites (323 web tests), vet, gofmt, both builds, and a new test pinning the chart-font
normalization.

The font change was rendered rather than reasoned about: wkhtmltopdf and poppler installed, a PDF
produced through the real export path — `renderPDFHTML` into `htmlToPDFContext`, not a hand-built
sample — with a chart deliberately carrying `font-family="Microsoft YaHei"` to prove the pinning
holds end to end. `pdffonts` on the result reports one embedded font, `NotoSansCJKsc-Regular`, and
nothing else.

Worth stating plainly, because the first diagnosis was wrong and the measurements are what
corrected it: this is not a blurry-to-sharp fix. Both the old font and the new one embed as vector
outlines, and at 300 dpi the old exports were already crisp. Measured at screen resolution the new
font carries noticeably more fully-inked pixels at the same text — heavier, more even strokes — and
the punctuation spacing is visibly repaired. Expect exports that read cleaner and set correctly,
not a different order of legibility.
