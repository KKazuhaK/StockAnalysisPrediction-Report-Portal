# v0.4.41 — dragging works, and works without a mouse

## Upgrade notes

From v0.4.40 — pull and restart. No schema changes, no settings, no API changes; one new string per
language. Rolling back to v0.4.40 restores the behaviour described below, including the lists that
could not be dragged.

## Fixed

**Two lists could not be reordered by dragging at all**, and gave no sign of why. The announcements
list was the one reported; the run-preset windows list had the same defect and nobody had noticed.
Grabbing a row did nothing — it did not follow the pointer, it did not change place, and no error
appeared anywhere.

The cause is one line at each site. Dragging is clamped so a row cannot be thrown out of its list,
and the clamp is defined against the dragged row's *parent element* — which does the intended thing
only while every row in the list shares one tall parent. Both pages had reached for antd's `<Space>`
to get the gap between rows, and `Space` puts each child in its own box, exactly that child's size.
The clamp then had nothing to move within, so it pinned every row where it stood.

Swapping the two `<Space>` elements for plain containers would have fixed today's bug and left the
trap: the next person adding a list reaches for `Space` for the same reason, to get a gap. The
shared wrapper now renders the list container itself and takes the gap as a prop, so a caller has no
reason to interpose anything, and the test that pins this includes one which reproduces the failure
deliberately — three rows under three parents — so the reasoning survives whoever reads it next.

**The batch run-targets table could not be sorted either**, for an unrelated reason found while
checking the rest. The table tells the drag layer each row's key with whatever type the row's id
has, so a numeric id arrives as a number while the list of ids around it holds strings; the drag
layer matches by identity, so `1` never found `"1"` and every row registered as belonging to no
list. This is now normalized in the single place that reads the key, so a table cannot get it wrong
by having numeric ids.

**Reordering was impossible without a mouse, on every sortable list in the console** — while each
one announced to a screen reader that it was possible. The drag layer publishes instructions
unconditionally ("To pick up a draggable item, press the space bar"), and marks every row as a
sortable item, but only a pointer sensor was ever registered: the space bar did nothing. Ordering is
the whole mechanism on these pages — there is no move-up button and no order field anywhere — so
that made announcements, links, SSO rules, batch targets, run presets and report types
mouse-only, with nothing on screen to say so. The keyboard sensor is now registered, and both drag
surfaces take their sensors from one place so they cannot drift apart again.

**Every row was a tab stop that did nothing, and stopped being a row.** The sortable markup was
applied to the whole row rather than to its drag handle. On a table that overrides a `<tr>`'s
implicit role, so a screen reader can no longer walk the table by row and column; on the
announcements and links lists it wrapped a switch, an Edit button and a delete confirmation inside a
single control, which is invalid and reads as one thing. It also put a focus stop in front of every
row that responded to nothing, because the only element the drag layer listens to is the handle. The
markup moves to the handle, where it is true — and the handle, an icon-only button, now has a name
instead of being announced as an unlabelled button on every row of every list.

**An empty table offered its "no data" message as a draggable item.** The placeholder row goes
through the same row component with no key, so it registered as a sortable item literally called
`undefined`, reachable by Tab and announced as draggable. It is a message; it is no longer either.

## Verification

Web typecheck, 507 tests across 74 files, locale parity, and the SPA build. Go build, vet, gofmt and
the full Go suite.

Every place in the portal that involves dragging was checked, not only the one reported: the
announcements list, entry links and their groups, report types, SSO rules, batch run targets and run
presets. Two of them were broken outright and one silently refused to sort; the accessibility
defects were on all of them at once, because all of them share the same helper.

The new tests are written against the DOM the drag layer actually produces rather than against its
documentation — the attribute names and types involved were confirmed by rendering the real
components, since being wrong about exactly these details is what produced the bugs. They pin that
the sortable rows are siblings of one another; that a spacing wrapper defeats the clamp, which is
why the container belongs to the shared helper; that a numeric row key registers under the string id
the list was given; that the sortable markup is on the handle and not on the row or the table row;
that the empty-table placeholder is not draggable; and that the space bar picks a row up, which is
what the instructions have been promising all along.
