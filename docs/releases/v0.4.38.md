# v0.4.38 — one prompt and one reload per deploy

## Upgrade notes

From v0.4.3 or later — pull and restart. No schema changes, nothing to configure, no new strings.
Everything here is in the SPA and the service worker.

**This is the last upgrade that will do it to you.** The fix is in the build being upgraded *to*,
so the tab you accept this release in is still running the old logic and may still ask twice. From
v0.4.38 onward a deploy is one banner and one reload.

Rolling back to v0.4.37 is clean — and reintroduces the behaviour below.

## Fixed

**Accepting a new version prompted twice and reloaded twice.** A deploy raises two independent
signals: `/api/version` is polled, and notices within five minutes or when the tab becomes visible;
the service worker only re-fetches `/sw.js` when the browser navigates. Accepting the banner
resolved whichever of them happened to be ready — usually the first, since the version poll is what
sees a deploy soonest.

With nothing waiting to hand over to, accepting did a plain reload. **That reload is a navigation**,
so it fetched the new `/sw.js` on the way, which installed and then waited. The page landed running
the **new build's HTML under the old service worker**, with a new worker waiting beside it — and the
banner reported it, correctly, as an available update. Accepting a second time did the handover and
reloaded a second time. One deploy, two prompts, two reloads.

It was intermittent because it turned on whether the browser had already re-checked `/sw.js` before
the click. If it had, the first click did the handover and there was no second prompt.

**Accepting now finishes the handover.** Where nothing is waiting, it asks the registration to
update, waits for what that turns up, and hands over to that. One click, one reload, and the page
ends up controlled by the build it is running — so there is no second prompt, and no cache left
over from a build nobody is running any more.

**A tab that did not accept was reloaded out of nowhere.** When one tab accepts, the new worker
claims every other open tab as it activates. Their cache is purged and the build they are still
running is no longer served, so the first lazily-loaded route they visit asks for a chunk that
exists nowhere and `lazyRetry` reloads the page under them. That is recovery, not an explanation —
which is what "it refreshed by itself a while later, or after I did something" was.

Such a tab now raises the banner instead, so the reload is the reader's decision like everywhere
else. Accepting there is a plain reload: the worker it would have handed over to is already the one
in charge.

## Notes

Both waits when accepting are bounded — three seconds for a freshly-fetched worker to install, two
for it to take control — and past either the page reloads regardless. A button that appears to do
nothing is worse than a reload that skipped a step.

None of this is reachable without the PWA switched on: with no service worker registered there is
only the version signal, and accepting it was always a plain reload and always right.
