# v0.4.10 — the SSO guide works before you have configured SSO

## Upgrade notes

From v0.4.3 or later — pull and restart. No schema change, no settings change,
nothing to re-enter.

One thing you may notice rather than a step you have to take: if the site's
public URL is not set (Manage → General → Address), the SSO setup guide now
says so instead of showing addresses. It was showing empty boxes.

## Fixed

**The setup guide's addresses were empty on exactly the portal that needed
them.** The guide shipped in v0.4.9 pairs each value an admin must paste into
their identity provider with the name of the box it goes into. On a portal that
had never saved an SSO provider, both values came up blank — which is every
portal reading the guide for the first time, since configuring the IdP is step
one and saving the portal side is step four.

The addresses were only sent per stored provider row. They do not depend on a
stored row: they are the public URL plus a fixed slug, and the admin UI offers
exactly one SAML and one OIDC provider, so the slug before saving is known.
`GET /api/admin/sso/providers` now returns them as `sp_defaults` alongside the
rows, and the page seeds an unsaved provider from those. A test pins that a
saved provider's addresses are the *same strings* — teaching one value while
the server accepts another is worse than teaching nothing, because it fails at
someone else's sign-in rather than at the form that caused it.

The guard that should have caught this let it through. It rejected a value that
was a bare path — what the server derives with no public URL configured — but
accepted a blank, on the reasoning that an absent value is not a wrong one. On
screen a blank is an empty box beside a copy button, which reads as a value
exactly as much as a relative path does. Every value must now be an absolute
URL or the guide shows none of them and says why.

## Changed

**The setup guide starts folded.** It is reference material read once; the
settings underneath it are what an admin comes back for, and those should not
start a screen further down the page than they used to.

## Verification

Go and web suites, vet, staticcheck, gofmt, both builds, the Postgres
integration tests, and `scripts/e2e_check.py`.

The endpoint was also exercised against a running portal rather than only in
tests, because the defect this release fixes was invisible to the tests that
existed: with no public URL it returns relative paths and the guide refuses
them; with one set it returns the absolute addresses, before any provider has
been saved.

Also fixed the one CI failure that had outlived three releases. The mermaid
cache test asserted a write that happens one commit AFTER the SVG it waited
for, so a loaded runner reported zero calls — and the pending write then
flushed during testing-library's cleanup, which runs after the suite's own
`afterEach`, so it surfaced as the *next* test's first call. Both assertions
now wait for their own arguments, and the mocks are cleared before each test
rather than after, which a late call cannot outrun. Reproduced deterministically
by delaying the effect one macrotask before fixing it; the component was never
wrong.
