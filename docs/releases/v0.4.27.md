# v0.4.27 — the text under an exported page is the text you typed

## Upgrade notes

From v0.4.3 or later — pull and restart. No schema changes, nothing to run by hand, and rolling back
is clean.

**PDFs exported by v0.4.23 through v0.4.26 have a corrupted text layer.** They look correct and
print correctly; the defect is invisible on the page. If you have archived exports from those
releases and anything downstream reads their text — a search index, a model re-reading a report, an
accessibility tool — re-export them. Rendering is unchanged, so a re-export differs only in the text
layer.

## Fixed

**Every ideograph with a radical lookalike came out of the text layer as the radical.** Search inside
an exported PDF for 月 and it found nothing; copy a paragraph out and you got ⽉ KANGXI RADICAL MOON,
a character nobody typed. Measured on a real 8-page report: zero occurrences of 一, 月, 无, 行, 目 or
风, and 130 occurrences of their radical twins. The page itself was never wrong — the two codepoints
draw the same glyph — which is why this shipped three times without anyone seeing it.

Noto Sans CJK SC addresses those glyphs twice, once as unified ideographs and once through the Kangxi
and CJK Radicals Supplement blocks. That is correct font data; dictionaries need to address a radical
directly. It goes wrong one layer up: wkhtmltopdf's Qt builds the PDF's ToUnicode table by
reverse-mapping glyph back to codepoint, and where a glyph has several it takes the lowest, which is
always the radical.

This arrived with the font switch in v0.4.23 and was verified as a regression rather than assumed —
the same text through the same renderer extracts as ideographs under WenQuanYi Zen Hei and as
radicals under Noto Sans CJK SC. The upstream SC subset build behaves identically, so it is a
property of Noto CJK rather than of one file.

The build now runs `scripts/strip-radical-cmap.py` over the font before installing it, removing 658
radical-block mappings so each glyph has exactly one codepoint left. Nothing stops rendering: the
glyphs stay, only the second way of naming them goes, and no codepoint in the coverage corpus lives
in those blocks. The font grows shorter by 4,588 bytes.

## Added

**The coverage gate now also asserts that nothing claims the radical blocks.** Coverage was never the
issue here — the font covered everything and still produced the wrong text — so the gate gained a
second, different invariant: no installed font may claim U+2E80–2EF3 or U+2F00–2FD5. Installing an
unpatched CJK font fails the build with an explanation rather than shipping a quietly wrong text
layer. Exercised both ways: unpatched fails with "claims 3 range(s)", patched passes, and the
existing colour-emoji refusals still fire.

Worth recording because it nearly shipped broken: the first draft of that check compared against
`0x2E80` literals. POSIX awk has no hex constants and mawk is the awk in this image, so those read as
zero and the check passed on the very font it was written to reject. It reads its bounds through the
same `hex()` helper as the rest of the script now. This is the second time a hex assumption has bitten
this script — `strtonum` was the first.

**CI builds the font chain on every push.** `Dockerfile.release` used to be executed for the first
time during a release, so a mistake in it surfaced after the binaries were built — and, before the
release job learned to wait on the image, after the GitHub Release was already public. Two v0.4.24
attempts were lost that way, one of them to `wget -nvO`, which is not a valid option spelling.

The Dockerfile is now staged, and the new `font chain + coverage gate` job builds `--target
runtime-base`: everything up to and including the gate, stopping before the stage that copies the Go
binary, so it needs no build artifacts. Fonts are fetched, the cmap is patched and the gate runs, on
every push and every pull request.

The font-patching stage is also pinned to `BUILDPLATFORM`. Its output is a font file, identical
whichever architecture produced it, and leaving it on `TARGETPLATFORM` would run Python over a 16 MB
font under QEMU on the arm64 leg for nothing.

## Verification

Go suite, web typecheck, web tests, the SPA build, vet and gofmt.

The regression, the mechanism and the fix were each measured rather than reasoned about: an uploaded
report was parsed codepoint by codepoint to establish the corruption, the same string was rendered
under both fonts to establish which one caused it, the upstream subset build was rendered to rule out
a one-file explanation, and the patched font was rendered and extracted to confirm
一月无行目风长门贝车 round-trips exactly. The gate was run against unpatched, patched, CBDT-colour and
COLRv1-colour font sets.

Two things this release does not fix, both carried forward from v0.4.24: `<pre>` still resolves to a
proportional face, and symbols are drawn smaller and lighter than surrounding text by the CJK face
itself.
