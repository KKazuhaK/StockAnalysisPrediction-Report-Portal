# v0.4.44 — a corrected report says so, and a drag stops losing things

## Upgrade notes

From v0.4.43 — pull and restart. No schema changes, no settings, no new strings. Nothing to do.

Rolling back to v0.4.43 is clean and restores the behaviour described below, including the two ways
a drag could lose work.

## Fixed

**A hand-written correction appeared next to the workflow's own report as a second tab called
"深度分析 2".** Two tabs, the same name, a digit, and nothing to say which one a person wrote.

The number was always there, for a good reason: a report's identity includes its title, so one
code + date + subtype legitimately carries several genuinely different reports, and the number is
what tells them apart. It was simply the wrong answer for a case that until now barely happened —
no workflow sends a version, so two *written forms* of one analysis (v0.4.39's report versions)
were rare. One hand-written correction (v0.4.42) produces it every time.

Now a tab that is a different written form of the same report is named — **深度分析 · 人工** — and
the number counts distinct reports rather than rows, so every form of one report carries that
report's number. The workflow's own keeps the bare label, and a portal that has never used versions
reads exactly as it always did. The suffix is the version's own label from 管理 → 报告版本, so
renaming it there renames it on the strip.

**Dragging a report type could bring back one you had just deleted, permanently.** The strip posts
the list the browser last read, so a type deleted since — by you in another tab, or by a colleague —
was still in it, and the save is an upsert: it created the row again, uncategorised and unlabelled,
back in the reader's category filter and every run form. Deleting it a second time only held until
the next drag.

Reordering now writes only names that still exist. It is not a creating operation, and the upsert
stays where it is genuinely needed: a *discovered* type — one that reports carry but nobody has
configured — still gets a row created when you drag it, because it has none to update.

**Dragging entry buttons could move them into a deleted group, where nothing would ever show them
again.** Same shape, worse ending: the buttons were stamped with a group id nothing resolves, which
hid them from the home page *and* from the entry-buttons admin page at once. There was no way back
through the interface — re-creating the group gets a new id — so recovery meant editing the database
by hand.

A header naming a group that no longer exists now sends the buttons under it to the top level, which
is exactly where deleting a group already puts the links it was holding.

**Three of the four drag-to-sort surfaces could not tell you a save had failed.** Entry buttons
discarded the error outright; report types and batch run targets raised one nobody was listening for,
because the drag helper does not await what it calls — so on those two the corrective reload was
skipped as well. In every case the admin was left looking at the order they had just made, with the
list quietly reverting on their next visit. On the entry-buttons page it was worse than cosmetic:
the same save carries each button's group membership.

All three now say so and reload, which is what the announcements list has done since v0.4.39. The
server stopped discarding its own errors too: two of the three reorder endpoints looped through the
writes and answered "ok" regardless, so a half-applied reorder reported success.

**The run-targets table could render an order the server does not hold.** It is the one list on the
page refetched from four different places, and two of those requests could be in flight at once with
no ordering between their answers — the slower one won. Because the table is also what the next drag
reads, that stale view then got written back. Only the newest request may now update the table.

## Verification

Web typecheck, 520 tests across 76 files, locale parity, and the SPA build. Go build, vet, gofmt and
the full Go suite.

The new coverage is the two data-losing cases and the labelling, each confirmed by removing the fix
and watching the test fail: that a stale drag cannot recreate a deleted report type while a
discovered type still gets its order row; that a stale drag sends buttons to the top level rather
than into a group that no longer exists, while an ordinary drag still groups and orders normally;
and that a tab names the written form, numbers distinct reports, gives every form of one report that
report's number, and leaves a version-less portal's labels untouched.
