# v0.4.44 — a workflow's cache is not a report

## Upgrade notes

From v0.4.3 or later — pull and restart. No schema change, no migration, nothing to
re-enter. Rolling back to v0.4.43 works and simply brings the hidden entries back into
view; nothing is rewritten either way.

## Fixed

**Pipeline cache entries no longer show up as reports.** `获取公司基本信息` writes a
per-symbol, per-day facts snapshot so that its thirteen callers do not each spend ~47s
re-fetching the same numbers from the same upstream. The portal exposes no key-value
store, so that snapshot is stored the only way anything durable can be stored here — as a
report. The result was a 未分类 tab on every stock analysed that day, with one card in it
that no human ever wanted to read, sitting next to the reports they did.

Four reader-facing paths now skip these entries: the stock detail page, the browse and
search feed, the day export (so a reader's ZIP holds reports and nothing else), and the
subtype picker in the report editor.

That last one is not cosmetic. A report's identity is `symbol|date|subtype|title`, so a
hand-written report filed under a cache's subtype lands in that cache's namespace and is
handed back to the workflow that believes it is reading its own snapshot. Offering the
type in a writer's dropdown was an invitation to corrupt it. Type management still lists
it: an admin seeing what exists in the data is useful, a writer being able to pick it is
not.

Two paths are deliberately left alone. `GET /api/v1/reports` and the v1 manifest are how
the producing workflow reads its own cache back — filtering there would silently disable
the cache and send every caller to the slow path, with nothing in the UI to show for it.
And the comparable-reports list needs no filter of its own: it is scoped to the same
symbol *and* subtype, so once the stock page stops handing out snapshot ids there is no
way to ask about one.

New plumbing types are one line in `internalTypes`.
