# v0.4.22 — confirm your identity the way you sign in

## Upgrade notes

From v0.4.3 or later — pull and restart. One additive column (`auth_requests.purpose`) is added on
first start; nothing to run by hand, and an empty value means "sign-in", so every row written by an
earlier build keeps the meaning it had.

**Read this if your login mode is "SSO only (auto-redirect)".** Confirming your identity now
requires a round-trip to the identity provider — the password box is no longer drawn for ordinary
accounts. Admins keep the password channel, so a broken IdP cannot lock an operator out of fixing
it. If no provider is enabled the whole thing degrades and the password channel stays open.

## Fixed

**Under force-SSO the confirm dialog demanded a credential the portal refuses.** `sso_only` stops
`/api/login` accepting a local password, but the step-up still took one — so re-proving your
identity was *weaker* than signing in. That is backwards for a control whose entire job is to be
harder than the session it protects.

**Someone who signs in through an IdP every day was asked for a password they never type.** An SSO
login that matches an existing local account by username or email does not make that account
federated: it keeps its password hash, and the dialog kept asking for it.

(Accounts owned by a provider — `source` is not `local` — are unaffected and deliberately so. The
password, 2FA and passkey cards are not shown for them at all, because the provider owns those
factors.)

## Added

**A third way to re-prove your identity: a round-trip to the identity provider.**

It only counts if the provider actually re-authenticates — **SAML `ForceAuthn`, OIDC
`prompt=login`**. Without that the IdP answers from its own session and returns instantly, which
proves nothing about the person at the keyboard: the case this mechanism exists for is an attacker
holding the browser, and the IdP session lives in that same browser. A provider that refuses
`ForceAuthn` fails the round-trip, which is the right outcome — better a step-up that cannot
complete than one that certifies nothing.

Three properties worth stating, because each is a way this could have been built wrong:

- **It matches, it never provisions.** The returning assertion is resolved with the matching half of
  the login path only. A step-up that could create an account would be a sign-up route behind a
  dialog captioned "confirm your identity". The resolved account must equal the one that asked.
- **The proof is a single-use HttpOnly cookie, not a token in the URL.** JavaScript never handles
  it; the page simply retries the request it was blocked on. A URL would be written into every
  reverse-proxy access log, kept in history, and leaked in the `Referer` of any subresource — the
  same reasoning that put the existing proof in a header rather than a query string.
- **It is outside the login lockout, deliberately.** There is nothing here to guess at, only a
  cookie the browser either holds or does not.

**The dialog offers what the login mode allows**, decided server-side:

| Login mode | Password / 2FA code | Identity provider |
| --- | --- | --- |
| Password only | yes | — |
| Password + SSO, SSO first | yes | yes |
| SSO only — ordinary account | **no** | yes |
| SSO only — admin | yes | yes |

The admin exemption is the one `sso_only` already carries, not a second differently-shaped one. With
no provider enabled the mode degrades exactly as `loginMode()` already degrades: refusing the
password channel while offering nothing in its place would strand every non-admin at once.

**No automatic redirect.** The dialog says why single sign-on is the way through and waits for a
click, rather than bouncing someone to a provider they did not ask for. With no password channel the
confirm button is not drawn at all — a button that cannot submit anything is a dead end. The
interrupted action resumes by itself on the way back.

## Changed

**Dependency advisories cleared.** `undici` (via `jsdom`, a devDependency — never in the shipped
bundle, never in the Go server) and `postcss` (via `vite`, likewise build-time) are bumped;
`npm audit` is clean. `golang.org/x/image` goes to v0.43.0, taking `govulncheck` from five
not-called module findings to one — `x/crypto/openpgp` being unmaintained, which has no fixed
version and which this portal does not import.

## Verification

Go and web suites (323 web tests, 9 new), vet, gofmt, both builds, and `scripts/e2e_check.py`.

The new Go tests pin the table above plus the proof's own properties: single use, bound to its
account, and an unfinished round-trip never counting as a finished one.
