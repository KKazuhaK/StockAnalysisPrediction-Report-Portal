# v0.4.1 — SSO, two-factor, report versions, captcha, self-service registration

A patch number that badly understates its contents. Everything from v0.3.10
onward lands here, because keeping the migration in this release line is what
lets a v0.3.10 database upgrade in ONE step: a 0.5 boundary would fold the
migration into the base schema and force production through a 0.4.x first.

UPGRADING FROM v0.3.10 — read this.

Back up the database first. This release rebuilds the unique index that
defines report identity: it backfills a version onto every row, drops the
four-column index and creates a five-column one. Verified twice against a
database built by the v0.3.10 binary itself, on SQLite and on Postgres — row
counts unmoved, bodies untouched, and two thematic reports distinguished only
by their titles still two. But it is a drop-then-create, so a process killed
between the two steps leaves the index briefly absent; the next start rebuilds
it, and only refuses if duplicates were written in that window. A backup makes
the question moot.

v0.3.10 is the last release of the 0.3 line, so it may jump straight here. An
older 0.3.x must reach v0.3.10 first.

Schema: eleven new tables, sixteen new columns, ten new indexes, one rebuilt.
Nothing is dropped and no column changes meaning. Fifteen new `meta` settings,
none of which are written on upgrade — every one defaults to the closed
position, so nothing turns on by installing this.

## What's new

SSO — SAML 2.0 and OIDC, one provider, admin-configured. Accounts link by
(issuer, subject) and never by email. Group rules assign role AND organizational
unit, because the OU is the real permission boundary.

Two-factor — TOTP with one-time recovery codes, and WebAuthn passkeys as a
second factor rather than a passwordless entry point. Every credential change
re-proves a factor and shares the login lockout. Users manage all of it
themselves at /account.

Report versions — one analysis published in several written forms, each from its
own run. Reading is a version grant plus a per-version visibility mode
(only mine / my group's / everyone's), addressable at an OU or a single account
and decoupled from who may RUN anything, which is what makes a read-only client
possible. This closes a disclosure present in v0.4.0: same-day reuse handed an
entitled external OU the internal report verbatim.

Captcha and self-service registration — both off by default. A self-hosted image
captcha needing no external service, plus Turnstile, reCAPTCHA and hCaptcha.
Registration creates the account disabled until its email is confirmed, and a
registrant with no OU configured can sign in and read nothing until an admin
places them.

Also fixed — the OU tree could not be built through the product at all
(SetGroupParent had no API and no UI), which silently disabled every inherited
setting; and four deletion paths left rows in the report viewer list, one of
which let a reused username inherit the previous holder's readable reports.

## Verification

Go and web suites, vet, staticcheck, govulncheck, both builds, and the Postgres
integration tests. scripts/e2e_check.py drives 77 assertions through the real
HTTP surface: run once on a fresh install and once on a real v0.3.10 database
upgraded in place.
