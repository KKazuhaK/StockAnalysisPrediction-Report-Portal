# v0.4.46 — a way to copy the database, and a way back from a rotated key

## Upgrade notes

From v0.4.45 — pull and restart. No schema changes, and nothing in the running portal behaves
differently.

Two operational gaps close here, both of the same kind: something a deployment is expected to be
able to do, that nothing in the product could do.

**Take a backup now.** The command exists as of this release:

```bash
docker compose exec report-portal /app/report-portal backup - | gzip > dump-$(date +%F).gz
```

Keep the `./config` directory beside it. `secret_key` lives there and is deliberately *not* in the
dump, so a backup without it restores everything except working SSO.

## Added

### `backup` and `restore`

Everything the portal owns is rows: accounts, groups and the OU tree, report bodies, the hand-written
versions and their revision history, installed apps and their files, tokens, webhooks, recurring
tasks, and every setting that is not one of the six lines in `config.yaml`. There was no way to take
a copy of any of it and no way to put one back — not a command, not an endpoint, not a paragraph.

That was not a theoretical gap. The Docker stack keeps Postgres in a named volume, and
`docker compose down -v` — the documented way to reset a stack, and the first thing anyone tries when
a container misbehaves — deletes it. The release image carries the portal and nothing else, so there
is no `pg_dump` inside to reach for either.

```bash
report-portal backup dump.jsonl          # the whole database; "-" writes to stdout
report-portal restore dump.jsonl         # dry run: validates and reports, writes nothing
report-portal restore dump.jsonl --force # replaces the database (stop the portal first)
```

**Without `--force`, `restore` is a dry run.** It reads and validates the entire file and tells you
what it would load and exactly how many existing rows it would delete. That is deliberately two
things: it makes "is this backup actually readable?" a question you can answer on a live system
without a spare database, and it means no arrangement of arguments replaces a database by accident.

**One format for both drivers**, so the runbook has one line in it whichever driver you run — and so
a dump is portable *between* them. "We outgrew SQLite" and "we want to go back to a single file" are
now a backup and a restore rather than a migration project.

**A restore is a replacement, in one transaction.** Every table in the schema is emptied, not only
the ones the dump carries, because a table the dump omits must end up empty too; anything else is a
mix of two databases that never existed. A dump cut short by an interrupted download or a full disk
leaves the target byte-identical.

`-` means stdin/stdout, so compression stays your choice: `backup - | gzip` and
`zcat … | restore - --force` compose with the tools you already have.

Design notes, including why this is not a wrapper around `pg_dump`, are in
[ADR 0027](../adr/0027-backup-and-restore.md).

## Fixed

### Rotating `secret_key` permanently wedged the SSO keyring

Stored auth secrets — the OIDC client secret, the SAML SP private key — are encrypted with a data
key, and only that data key is wrapped under `secret_key`. The comment at the top of the file has
said since ADR 0023 that rotating `secret_key` therefore "re-wraps ONE row instead of re-encrypting
every stored secret".

That code was never written. Rotating `secret_key` left the data key unopenable: SSO down, captcha
silently failing, and no page able to repair it — because saving a secret needs the very key that
will not open. The ADR's own consequence section pointed at a `rotate-kek` command that does not
exist.

It exists now, as the config it should always have been:

```yaml
secret_key: "the new one"
secret_key_previous: "the one you rotated away from"   # or RP_SECRET_KEY_PREVIOUS
```

Restart once and delete the second line. Exactly one row is rewritten; the data key itself does not
change, so every secret already sealed under it stays readable and nothing is re-entered. The portal
logs a line on every boot while `secret_key_previous` is still set — it is harmless, but it is a
second live key on disk.

Rotating **without** it still fails, and that is the correct behaviour: minting a fresh data key
would silently orphan every secret already stored. What changed is that the failure now names both
ways out — restore the old key, or delete the two keyring rows from `meta` and re-enter the SSO
secrets — instead of an opaque decryption error.

`config.example.yaml`, the generated first-run config, the README and ADR 0023 all describe the
procedure now.

## Verification

Go build, vet, gofmt and the full Go suite; web typecheck, the full web suite, locale parity and the
SPA build.

The backup path is tested for the things that would lose data quietly rather than loudly: a 2^60 id
survives JSON as itself (a `float64` would round it), NULL restores as NULL rather than a zero value,
binary content comes back byte-for-byte, and re-dumping a restored database produces the same bytes
as the original dump. A dump that carries a table or column this build has no schema for is refused
by name rather than dropped; an *older* dump loads with the new columns at their defaults and reports
which ones those were. A truncated dump is proven to leave the target byte-identical — confirmed by
removing the rollback and watching the test fail.

Postgres is covered by its own integration tests rather than assumed, because the parts that differ
are exactly the parts that fail silently: an identity column rejects an explicit id without
`OVERRIDING SYSTEM VALUE`, and its sequence does not move when one is supplied, so the first report
written after a restore would collide with one just loaded. Both were confirmed by removing the fix
and watching the tests go red — the sequence test winds the sequence back first, because a previous
run would otherwise leave it high enough to pass no matter what. A dump also round-trips SQLite →
Postgres → SQLite with its binary column intact.

The key rotation is tested for the lossless case, for the next boot (the re-wrap persists, and the
retired key stops working), for a refused rotation leaving the keyring untouched and the old key
still able to recover it, for a wrong previous key, and for a stale `secret_key_previous` left in the
config being a no-op rather than a re-wrap backwards.
