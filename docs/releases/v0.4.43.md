# v0.4.43 — a report remembers what it used to say

## Upgrade notes

From v0.4.42 — pull and restart. One table (`report_revisions`) and one column (`reports.author`)
arrive on the first boot; there is nothing to run. No API contract changes.

Two things are worth knowing before you upgrade.

**Nothing written before this release has an author.** The column arrives empty and there is no
backfill — the audit log is where "who wrote this" lives for anything older. In practice that is
every report you have, since hand-written reports are one release old.

**The new retention target ships switched off, like every other one.** Turning it on deletes edit
history by age. Read the note about it below before you do: it is the first target whose rows age
independently of the thing they belong to.

Rolling back to v0.4.42 is clean but not lossless in one direction. The table and the column stay on
disk and the older build ignores both, so nothing is destroyed — but the older build's saves write no
history, so anything edited during a rollback has a gap in its record that cannot be filled in
afterwards.

## Added

**A hand-written report keeps what it used to say.** 管理 → the report editor now has a **历史**
button: every version the report has been, newest first, with who saved it and when. Open one and
you get the changes against what the report says now — the same section diff the report comparison
uses — or the old version rendered as a document, whichever question you are asking. There is a
**还原** on each.

The history is what the report *used* to say. The current text is not in the list, because it is not
history — it is the report, and it sits above the list as the thing every entry is compared against.

**Restoring cannot lose anything.** A restore is an ordinary save, so the version it replaces is
filed in the history like any other: restoring is undone by restoring again. That is what makes the
button safe to press without reading the whole document first, which is the only way a restore button
gets used.

It also means a restore inherits every rule a save already follows. It is refused if somebody else
saved while you had the history open. It puts the title, the code, the date and the subtype back too
— a restore that recovered the words under the wrong title would be a different report wearing the
old text — and because that is a rename, it can collide with another report exactly as renaming can,
and says so.

**Two ways to bound how much history is kept, and they are not the same mechanism.**

*Per report, by count.* 管理 → 存储 has **每篇保留版本数**. The default is **0, meaning keep every
version** — which is what an unconfigured portal does, and what you asked for. Set it to 20 and each
report keeps its most recent 20; the trim happens when a report is saved, inside the same transaction,
so the cap can never be exceeded even briefly.

*Across the portal, by age.* The storage console has a fifth retention target, **编辑历史**, off by
default with a 14-day floor. It appears in the usage breakdown beside the others, so you can see what
history is costing before deciding anything about it.

The floor is short on purpose. A revision is a recoverable copy of something that still exists, not
the thing itself — the same argument the audit log's 30-day floor rests on, one step further.

## Changed

**Reports know who wrote them.** `reports.author` is stamped on every hand-written save, and shown in
the editor's history. It is deliberately *not* shown on the reading page: the 人工 version label
already tells a reader the thing that changes how they read a report — that a person wrote it, not a
workflow — and naming that person to every reader is a disclosure nobody has asked for.

**The audit log distinguishes restoring from editing.** `report.restore` is its own action beside
`report.create` and `report.edit`, and records which version was put back. A restore is the one edit
whose content nobody composed just now, so "what did this say, and who decided it should say that
again" is only answerable if the log can tell it apart.

**The report comparison and the edit history draw the same picture.** The section renderer moved out
of the comparison dialog into one component both use, rather than the history growing a second way to
show a diff of the same server payload.

**The edit history is open to internal accounts only.** A version is authorized through its report,
and a report's audience can be changed — while a version, once written, cannot. So an external
account added to a report's recipients today would otherwise be able to read every version written
while it was addressed to somebody else, which is precisely what "take the internal detail out, then
add the client" produces. The history refuses any account whose reads are scoped, and says so.

Internal accounts holding the editing permission are unaffected, which is everyone who has it today.

## Notes

**Edit history ages independently of the report it belongs to**, and this is the first thing in the
storage console that does. Every save rewrites a report's own timestamp, so a report that is actively
edited never becomes eligible for the reports retention pass — while each of its versions is stamped
once and never touched again. Switching the history target on is therefore a decision to forget the
past of reports you are still writing. That is what it is for; it is worth knowing it is not
symmetrical with the reports target.

**A save that changed nothing writes no history.** Pressing save twice, or changing only who a report
is addressed to, would otherwise bury the version you want under identical copies of the one you are
looking at.

**Deleting a report deletes its history**, through both delete paths — the editor's, and the storage
console's age sweep. A version is a whole prior copy of a body, and leaving one behind would put a
deleted report's text on disk under an id that gets reassigned.

**The audience is not part of a version.** Who a report is for is not what it said, it lives in
another table, and a restore does not change it. A version that claimed to capture an audience it
cannot restore would be worse than one that plainly does not.

**The byline follows the text, not whoever last pressed save.** Changing only a report's recipients
records no version, and so does not move the author's name either — otherwise the next real edit
would file the previous author's words under the name of whoever had touched the audience in
between, with the original recoverable from nowhere but the audit log.

## Verification

Web typecheck, 519 tests across 76 files, locale parity, and the SPA build. Go build, vet, gofmt and
the full Go suite.

The new coverage is at the seam between a save and its history, because that is where this can go
wrong without anyone seeing it: that the log holds what the report used to say and never a second
copy of what it says now; that a refused save leaves the log exactly as it was; that a save changing
nothing records nothing while still moving the token; that a version carries the identity and not
only the body; that the count cap keeps the newest N and only for the report being saved; that the
cap is refused rather than clamped when it makes no sense, and survives an unrelated save through the
console's per-field merge; that the retention pass counts exactly what it deletes; that both delete
paths take the history with them; that restoring is itself recorded, is refused on a stale token, and
reports a collision when the old title has since been taken; that one report's history cannot be read
through another; and that a workflow's report refuses the history endpoints rather than answering
with an empty list, which would read as "nothing has been edited yet".

Several were confirmed by removing the behaviour and watching the test fail: the no-op suppression,
the storage sweep's cascade, the console target's dispatch, and the history's refusal of a scoped
reader. The refused-save guarantee rests on the snapshot being inside the save's transaction, which
is structural — verified by reading the path rather than by mutating it, with the stale-save test
covering the refusal itself.

This release was also reviewed adversarially across six dimensions, and the review is why several of
the properties above are pinned at all: the retention test had no row on the keep side of its cutoff,
so a predicate equivalent to "true" would have passed it; the console's whole fifth-target wiring was
untested, and three separate breaking edits each left the suite green; the list endpoint's response
shape was asserted only against a frontend mock that wrote it; and the disclosure and byline defects
above were found there rather than here.

One more thing the review changed rather than found: `zh-TW` had kept the pre-existing wording of two
storage strings that gained a `{{revisions}}` placeholder, because the generator only fills keys that
are *missing*. It now reconverts a key whose placeholders have drifted, and a locale test pins that
every language interpolates exactly what the base does — which is the general form of a bug that had
been silently possible for every translated string with a value in it.

On the browser side: that the history fetches nothing until it is opened, that it lists the
superseded versions and not the current one, that opening it leaves an unsaved draft untouched, and
that a restore is computed against the token the editor is holding rather than any other.
