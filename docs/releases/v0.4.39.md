# v0.4.39 — more than one announcement, in an order you choose

## Upgrade notes

From v0.4.3 or later — pull and restart. Two tables (`announcements`, `announcement_grants`) are
created on the first boot; there is nothing to run and nothing to configure. The announcement you
have configured today is folded into the first row automatically, keeping its text, level, and
popup switch, and set to show on the home page for everyone — so the day of the upgrade looks like
no change at all.

**One thing does change without being asked for: the announcement is no longer readable by signed-out
visitors.** It used to be published on `/api/site`, which has no authentication because the login
page reads it for the brand title — so the text was fetched, and re-fetched every minute, by anyone
who could reach the login page. It now comes from `GET /api/announcements`, which requires a
session. Nothing you have to do; worth knowing if you have ever put something on the banner on the
assumption that only signed-in people saw it.

**The management page no longer has a Save button.** Each announcement saves on its own, and
dragging one into place persists immediately — the entry-buttons page has worked this way for a
while and this now matches it.

Rolling back to v0.4.38 is clean but not lossless. The five old settings keys are still on disk, so
the old page still works, but the import switches the announcement off on its way past: a rollback
shows *no* announcement rather than an incident notice from days ago that the old form is the only
place to take down. Announcements created after this upgrade are not visible to v0.4.38, and edits
made from the old page during a rollback are not re-imported on the way back.

Readers keep their "don't show again" through the upgrade — the stored dismissal is matched against
the imported announcement and carried across, once.

## Added

**Several announcements at once, in the order you drag them into.** Manage → 站点 → 公告 is now a
list. Each row has its own level, title, body, on/off switch and popup switch; the order readers see
is the order in the list. Dragging is the whole ordering mechanism, and it only moves rows — it does
not count as editing them, so rearranging the list never re-interrupts a reader who has already
dismissed something.

**A popup switch per announcement.** It used to be one switch for the portal. At most one popup
appears per page load — the topmost eligible one — because closing one modal only to be handed
another is not a thing to do to somebody. Rows whose popup will not fire this way say so on the row,
so a switch that is doing nothing is visible where it was set rather than discovered later.

**An optional display window.** Give an announcement a start, an end, or both, and it appears and
retires on its own. This is the feature that keeps the rest of them worth reading: with one banner,
forgetting to take an incident notice down is embarrassing; with several, it is a screen of stale
warnings, and a band that is stale is a band nobody reads. A background tab retires an expired
banner by itself rather than showing it until somebody clicks back into the tab.

For the operator who will not set an end time, an announcement that is switched on, has no end date,
and has not been touched in two weeks gets an amber "up for N days" tag in the list — a nudge, not
a rule.

**Announcements can be closable.** Per row. The banner was previously permanent furniture for
everyone; now an FYI can be dismissed while a compliance notice stays pinned. Closing a banner is
remembered per announcement and per reader, and it stops only that banner: the popup rules are
separate, and "got it" on a popup stops it for the session while "don't show again" stops it for
good, both leaving the banner where it is.

## Changed

**Dismissals are now remembered per announcement and per person.** The old scheme stored one value
for the whole browser, so on a shared machine one person clicking "don't show again" silenced the
announcement for whoever used the browser next. Re-notification still works the way the interface
has always promised: editing what an announcement *says* shows it again; changing its schedule, its
switches or its position does not.

**The announcement no longer travels on the public site payload**, and that endpoint's field list is
now fixed by a test, so nothing can drift back onto it by accident.

## Fixed

Two pre-existing bugs, found because the new feed is the first authenticated poll that runs on every
page for every reader rather than only in the admin console.

**A shared browser could show the second person no polled data at all.** Conditional-GET tags were
remembered per URL for the lifetime of the page, not per session: sign out, sign in as somebody
else in the same tab, and the next poll sent the previous account's tag. The server could
legitimately answer "nothing changed" — which means *keep what you have* to a component that has
just been created and has nothing — and every poll for the next hour would confirm it, until a hard
refresh. Tags are now dropped whenever the signed-in identity changes.

**A session that had ended went unnoticed on a polled endpoint.** Polled requests threw without
reporting the expiry the way ordinary requests do, so the app kept believing somebody was signed in.
It is reported now, and the announcement feed clears itself on a 401 rather than leaving a targeted
notice on screen after the session behind it is gone.

**The zh-TW locale generator kept keys that no longer exist in zh-CN.** zh-TW is generated in full
and holds no hand-written text, so a key removed from the source stayed behind and broke the
locale-parity check with a message pointing at the wrong file. Removed keys are now dropped and
listed.

## Notes

The admin console and the mobile chat page never show the banner, whatever an announcement says.
Both are deliberately stripped layouts — chat hides the header to give the thread the viewport, and
the console is full-bleed with a rail measured off the header height — and a band on either adds a
scrollbar with nothing to scroll.

The schema carries two columns this release does not expose in the editor yet: showing an
announcement on every page rather than only the home page, and addressing one to a group or a person
instead of everyone. The reader side of both is built and tested; the editing side follows in the
next two releases, so each lands on its own and the one that changes who can see what gets reviewed
by itself. See `docs/adr/0025-site-announcements.md` for the reasoning, including why an
announcement addressed to a parent group reaches the whole subtree while a report-version grant
deliberately does not.

## Verification

Web typecheck, 481 tests across 73 files, and the SPA build. Go build, vet, gofmt and the full Go
suite. The new coverage is where the sharp edges are rather than spread evenly: that a rejected
reorder moves nothing and a stale one is refused; that dragging changes only the order and not the
timestamps a reader's dismissal depends on; that a row's inline switch cannot write back a stale
title or audience; that the public payload's key set has not grown; that the import runs exactly
once and does not resurrect announcements an operator deleted; that a dismissal survives an
announcement being switched off overnight; and that a targeted announcement reaches a child group
but not a sibling, and never reaches a caller with no principals.
