# v0.4.39 — announcements, plural

## Upgrade notes

From v0.4.3 or later — pull and restart. Two tables (`announcements`, `announcement_grants`) are
created on the first boot; there is nothing to run and nothing to configure. The announcement you
have configured today is folded into the first row automatically, keeping its text, level and popup
switch, and set to show on the home page for everyone — so the day of the upgrade looks like no
change at all. Readers keep their "don't show again": the stored dismissal is matched against the
imported announcement and carried across, once.

Three things change without being asked for.

**The announcement is no longer readable by signed-out visitors.** It used to be published on
`/api/site`, which has no authentication because the login page reads it for the brand title — so
the text was fetched, and re-fetched every minute, by anyone who could reach the login page. It now
comes from `GET /api/announcements`, which requires a session. Nothing for you to do; worth knowing
if you ever put something on the banner assuming only signed-in people saw it.

**The management page no longer has a Save button.** Each announcement saves on its own, and
dragging one into place persists immediately — the entry-buttons page has worked this way for a
while and this now matches it.

**One API contract changes.** `DELETE /api/admin/groups/{id}` now answers **409** when deleting the
group would leave an announcement addressed to nobody, until the caller says what should happen:
`?orphans=disable` switches those announcements off, `?orphans=keep` leaves them. Deletes that
orphan nothing are unaffected, and the admin console asks and passes the answer — so nothing changes
for somebody clicking through the UI. A script that deletes groups will need the parameter, and that
is the point: the silent path is the one being closed.

Rolling back to v0.4.38 is clean but not lossless. The five old settings keys are still on disk, so
the old page still works, but the import switches the announcement off on its way past: a rollback
shows *no* announcement rather than an incident notice from days ago that the old form is the only
place to take down. Announcements created after this upgrade are invisible to v0.4.38 — it does not
read the new tables at all — and edits made from the old page during a rollback are not re-imported
on the way back.

## Added

**Several announcements at once, in the order you drag them into.** Manage → 站点 → 公告 is now a
list. Each row has its own level, title, body, on/off switch and popup switch; the order readers see
is the order in the list. Dragging is the whole ordering mechanism, and it only moves rows — it does
not count as editing them, so rearranging never re-interrupts a reader who has already dismissed
something.

**A popup switch per announcement.** It used to be one switch for the portal. At most one popup
appears per page load — the topmost eligible one — because closing one modal only to be handed
another is not a thing to do to somebody. Rows whose popup will not fire this way say so on the row,
so a switch that is doing nothing is visible where it was set rather than discovered later.

**An optional display window.** Give an announcement a start, an end, or both, and it appears and
retires on its own. This is the feature that keeps the rest of them worth reading: with one banner,
forgetting to take an incident notice down is embarrassing; with several it is a screen of stale
warnings, and a band that is stale is a band nobody reads. A background tab retires an expired
banner by itself rather than showing it until somebody clicks back into the tab.

For the operator who will not set an end time, an announcement that is switched on, has no end date
and has not been touched in two weeks gets an amber "up for N days" tag in the list — a nudge, not a
rule.

**Announcements can be closable**, per row. The banner was previously permanent furniture for
everyone; now an FYI can be dismissed while a compliance notice stays pinned.

**An announcement can show on every page, not only the home page.** The editor has a "where it
shows" choice, and the two look different on purpose. The home-page card is the roomy one, on a page
somebody visits deliberately. A site-wide announcement gets a tinted band under the header, one row
per announcement, tinted by the most severe one in it — so a stack whose only incident notice sits
third does not read as a calm blue bar.

**Nothing folds by default.** Every announcement addressed to you is shown in full, on both
surfaces. If you end up running enough of them at once that this is too much, **管理 → 站点 → 公告**
has a site-wide "fold the extra announcements" switch: turn it on and each band shows the first with
the rest behind a "N more" link. Off is the default because hiding, behind a click, something you
decided was worth interrupting everybody with is not a saving.

Neither surface appears in the admin console or on the mobile chat page. Both are deliberately
stripped layouts — chat hides the header to give the thread and composer the viewport, and the
console is full-bleed with a rail measured off the header height — and a band on either adds a
scrollbar with nothing to scroll.

**An announcement can be addressed to a group or a person instead of everyone.** The editor gains a
"who it goes to" choice — *Everyone*, or *Chosen recipients* with a picker of groups and accounts —
and the list names the recipients on the row rather than printing internal ids.

Addressing a **group** reaches that group and everything under it. A notice sent to 华东 reaches
华东-上海 as well; a group having its own announcements never suppresses the company-wide ones. This
is the opposite of how report-version grants resolve, deliberately — a grant is a right, an
announcement is a broadcast — and `docs/adr/0025-site-announcements.md` says so at length, because
anyone reading the two tables side by side would otherwise assume they behave alike.

**"Everyone" includes external accounts, and that is the point.** The announcements that most need
to reach everybody — a maintenance window, a data source that is down — affect an external tenant
exactly as much as an internal colleague, and the tenant who was not told is the one who files the
support ticket. "Internal staff only" is expressed by addressing the group internal accounts belong
to, not by a separate setting; that works where those accounts sit in a named group rather than the
Default one.

**A "preview as" control**, beside the New button. Pick a group or an account and see exactly what
they would see right now.

This is not a convenience. **Administrators do not receive announcements addressed to groups they
are not in** — an announcement is a message, not a permission, and an admin who is not in 华东 does
not need 华东's outage popup on every page. That means a mis-addressed announcement fails silently:
you cannot see it, and the people who should have received it do not know to expect it. The preview
asks the server the same question a real reader's browser asks, so it cannot quietly disagree with
what people actually get.

The Default group is not offered as a recipient and is refused if sent: every account resolves
through it, so addressing it is addressing everybody under a name that reads like a subset — which
"Everyone" already says.

**An announcement that reaches nobody is flagged as such.** A targeted announcement cannot be
*created* with an empty recipient list, but deleting the group it was addressed to produces the same
state afterwards, and it would otherwise keep reporting itself as live: enabled, inside its window,
green tag, reaching no one. It now shows a red **"reaches nobody"** status with a tooltip saying
what to do about it.

**Deleting a group tells you what it will do to the announcements first.** A dialog lists them
before anything happens and separates the two cases that matter: the ones that **will reach nobody**
(this group was their only recipient) from the ones that **keep working** (they have others). You
then choose whether the orphaned ones should be switched off — the recommended answer, so that
nothing keeps pretending to be published — or kept as they are, where the list flags them. Neither
answer is applied for you: choosing on your behalf would be choosing whether a published
announcement quietly stops or quietly lies.

## Changed

**Dismissals are remembered per announcement and per person.** The old scheme stored one value for
the whole browser, so on a shared machine one person clicking "don't show again" silenced the
announcement for whoever used the browser next. Re-notification still works the way the interface
has always promised: editing what an announcement *says* shows it again; changing its schedule, its
switches, its recipients or its position does not.

**There is no limit on how many announcements you can have.** Refusing a save at the moment somebody
most needs to broadcast does not stop readers from ignoring an overcrowded band — it just stops the
broadcast. The console warns instead: past five announcements **live at once**, a yellow bar suggests
merging some, giving the older ones an end time, or switching a few off. It counts what readers
actually face, not the draft pile, so twenty drafts and two live announcements say nothing.

**The announcement no longer travels on the public site payload**, and that endpoint's field list is
now fixed by a test, so nothing can drift back onto it by accident.

## Fixed

**Deleting an account or a group left its announcement recipients behind.** Usernames can be
registered again and group ids are reassigned, so a stale recipient row would eventually be
inherited: the next person to hold a departed colleague's username would start receiving
announcements addressed to them. Both deletion paths now clear the rows, alongside the report-viewer
and version-grant rows they already cleared.

The guard against this is structural rather than a third hand-written case. A test reads the schema,
finds every table keyed by a recipient, and proves that deleting an account and deleting a group
each leave none behind — so the next such table fails on the day it is added rather than on the day
somebody notices the wrong person is reading something.

**Moving accounts between groups in bulk left no audit trail.** Changing an account's group decides
what that person may read and, now, what they are told. The single-account path has always recorded
it; the bulk action recorded nothing, so the fastest way to change many people's access was also the
only way to change it invisibly.

Two more, found because the new announcement feed is the first authenticated poll that runs on every
page for every reader rather than only in the admin console:

**A shared browser could show the second person no polled data at all.** Conditional-GET tags were
remembered per URL for the lifetime of the page, not per session: sign out, sign in as somebody else
in the same tab, and the next poll sent the previous account's tag. The server could legitimately
answer "nothing changed" — which means *keep what you have* to a component that has just been
created and has nothing — and every poll for the next hour would confirm it, until a hard refresh.
Tags are now dropped whenever the signed-in identity changes.

**A session that had ended went unnoticed on a polled endpoint.** Polled requests threw without
reporting the expiry the way ordinary requests do, so the app kept believing somebody was signed in.
It is reported now, and the announcement feed clears itself on a 401 rather than leaving a targeted
notice on screen after the session behind it is gone.

**The zh-TW locale generator kept keys that no longer exist in zh-CN.** zh-TW is generated in full
and holds no hand-written text, so a key removed from the source stayed behind and broke the
locale-parity check with a message pointing at the wrong file. Removed keys are now dropped and
listed.

## Notes

The recipient picker lists the first 200 accounts and says so when there are more; reaching an
account past that is done by putting it in a group. Groups are listed in full.

Deleting an *account* does not block the way deleting a group does. A group is the targeting unit
and deleting one is rare and high-impact; deleting an account is routine, already carries a long list
of consequences, and has a bulk path. The "reaches nobody" flag covers it.

The v0.4-line adoption step that folds the old single announcement into the new table lives in one
file named for the release line — `internal/app/upgrade_v04.go` — and is deleted whole at the v0.5
boundary, per ADR 0013. `POST /api/admin/settings` keeps its five announcement fields for one more
release line so a mid-upgrade rollback still has a working settings save; nothing sends them.

## Verification

Web typecheck, 498 tests across 73 files, and the SPA build. Go build, vet, gofmt and the full Go
suite.

The new coverage is where the sharp edges are rather than spread evenly: that a rejected reorder
moves nothing and a stale one is refused; that dragging changes only the order and not the timestamps
a reader's dismissal depends on; that a row's inline switch cannot write back a stale title or
audience; that the public payload's key set has not grown; that the import runs exactly once and does
not resurrect announcements an operator deleted; that a dismissal survives an announcement being
switched off overnight; that a targeted announcement reaches a child group but not a sibling and
never a caller with no identity; that the preview of an account agrees exactly with that account's
own feed; that a zero-recipient announcement reads as unreachable rather than live; that both bands show
everything until the fold switch is turned on, and that a folded strip never draws its lead twice
once expanded; that deleting a
group refuses without a decision and does not half-apply, while deleting one of several recipients
needs no decision at all; and the schema-walking recipient-sweep test, which was confirmed to fail
when a sweep is removed rather than passing for the wrong reason.
