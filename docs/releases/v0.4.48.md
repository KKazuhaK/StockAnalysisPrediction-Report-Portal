# v0.4.48 — a restart stops cutting requests in half, and cleanup gives the disk back

## Upgrade notes

From v0.4.47 — pull and restart. One additive column (`cleanup_runs.bytes_reclaimed`), picked up
automatically.

**Docker users get two behaviour changes for free**, both from the image and the compose file:

- The container now has a `HEALTHCHECK`. `docker compose ps` will start showing the portal as
  `healthy` / `unhealthy` where it previously showed nothing, and an unhealthy portal means its
  database is unreachable.
- `stop_grace_period: 15s` is set on the portal service. If you run your own compose file, add it —
  without it Docker's 10s default can SIGKILL the portal in the middle of the graceful shutdown
  below, which is the thing this release added.

## Fixed

### A restart cut every open request in half

The portal died on SIGTERM the instant it arrived. Every `docker compose restart`, every rolling
update, every Ctrl-C in a terminal: a report upsert answered with truncated JSON the caller has to
guess about, an export half-written, an audit entry that may or may not have been recorded.

It now stops accepting new connections and lets the requests already in flight finish, up to 10
seconds. What is still open at the deadline — an SSE stream, by construction, never ends on its own
— is closed then rather than waiting for the orchestrator's patience to run out. The database is
closed last, after the handlers are done, because closing it earlier would fail the very requests the
grace period was granted for.

The background loops (scheduling, cleanup, recurring tasks, the auth sweep) are deliberately not
drained. A batch run interrupted by a restart is already the case ADR 0015 exists for: the next boot
reconciles it from the queue rather than trusting the previous process finished anything. Waiting on
them would trade that guarantee for a slower stop and no more safety.

### `/healthz` could not see the failure that matters

It answered `{"ok":true}` unconditionally — which reports only the failure an orchestrator can
already see for itself, the process being gone, and stays green through the one it cannot: the portal
up, its database unreachable, and an error on every page. In the shipped Docker stack, where Postgres
is its own container, that is the realistic outage.

It now checks the database. The verdict is cached for a couple of seconds, so probing it — including
deliberately, since the endpoint is public and unauthenticated — costs at most one `SELECT 1` per
interval, which also keeps it from queueing behind a write on SQLite's single pooled connection. A
failure logs the driver's message for you and returns a bare "unreachable" to the caller, because the
error text can carry the DSN's host, user and database name.

The image carries a matching `HEALTHCHECK`, so `docker run` users get it too and not only compose
users.

### Cleanup deleted rows and freed no disk

The storage console reported "cleaned 12,431 rows" and `df` did not move — which is the number an
admin ran the pass to change. Deleting rows returns nothing on either driver: SQLite parks the freed
pages on the file's freelist, Postgres marks them reusable inside the table.

A pass that deleted something now ends by reclaiming, and reports the bytes it handed back — in the
success message, and in a new column on the run history.

On **SQLite** that is a `VACUUM`, gated: the freelist has to be at least a tenth of the file and the
file over about 8 MiB. The rewrite needs roughly the database's own size in temporary disk and blocks
every other query while it runs, so doing it for a handful of pages costs more than it returns. It
runs last, after the deletions, and never on a preview.

On **Postgres** it does nothing, on purpose, and the console says so. Autovacuum already reclaims for
reuse continuously; returning space to the operating system needs `VACUUM FULL`, which takes an
`ACCESS EXCLUSIVE` lock on every table it touches — an outage of unbounded length, scheduled by a
background ticker, on a database the portal does not own exclusively. A permanent zero with no
explanation looks like a bug, so it is explained.

## Verification

Go build, vet, gofmt and the full Go suite (Postgres integration tests included); web typecheck, 77
files / 528 tests, locale parity, and the SPA build.

Shutdown is tested against a real listener: a request is held open across a real SIGTERM, and it must
come back complete while new connections are already being refused — and the handler queries the
database on its way out, so the ordering is pinned too. Replacing the drain with an immediate close
truncates the body; closing the store first fails the handler. Both were confirmed.

`/healthz` is tested green, then tested against a closed database, and its response is checked for the
one thing a public endpoint must not leak: the driver's error text. The cache is tested in both
directions — a probe inside the window reuses the verdict, and the window expires.

Reclaim is tested for the number itself (the file shrinks by exactly what was reported), for the gate
(a database not worth rewriting is proven *not rewritten*, by its modification time, rather than
merely freeing nothing — which a full database does anyway), for the preview staying dry, and for
Postgres attempting nothing at all. Each of those four properties was confirmed by removing the code
that provides it and watching the matching test fail.
