# v0.4.50 — a failing request stops being invisible

## Upgrade notes

From v0.4.49 — pull and restart. No schema changes, no configuration.

**Your logs will get busier**, on purpose: API failures, every API mutation, and anything slower than
a second now appear where previously they appeared nowhere. Routine polling stays quiet, so the
volume should be small — but it is a change in what `docker compose logs` shows.

## Fixed

### API requests were not in the access log at all

The request logger skipped `/api/` outright, with a comment saying those endpoints "have their own
concise logs". They do not. A handful of handlers log one event apiece — an ingest, an app install —
and the rest log nothing.

So a 500 on an unaudited endpoint left **no trace anywhere**. The audit log records mutations it was
told about; reads, refusals and failures were invisible. "The page has been erroring since this
morning" had no evidence behind it, and neither did "it got slow".

The reason for the skip was real, though: the browser polls the home feed, the announcements and the
queue badge on a timer, once per open tab, so logging every API request would bury everything else.
The rule that keeps both properties is to log every API request **except a fast, successful read** —
which is exactly the polling traffic and nothing else:

- any status 400 or above, on any path
- any request taking a second or more
- every mutation (POST / PUT / PATCH / DELETE), including machine ingests
- every non-API request, exactly as before

Nothing that was logged before has stopped being logged. Static assets and `/healthz` stay silent;
they are high-volume and say nothing.

Each line now also carries the client address, resolved through the same trusted-proxy rules the rate
limiter and the audit log use — so a reverse-proxied deployment logs the visitor rather than the
gateway, and an upstream you have not trusted cannot write someone else's address into your log by
asking.

## Not in this release

**A `/metrics` endpoint.** The obvious companion to an access log, and deliberately not added here:
it is not a gap with one correct answer, it is a decision with a security posture attached. This
codebase has already taken a position that constrains it — `/healthz` is tested to expose no counts
and `/api/version` is session-gated, both so an anonymous scanner cannot read build identity or
business volume — and an unauthenticated `/metrics` carrying report and account totals would
contradict that. Gating it instead is perfectly workable (scrape configs take a bearer token) but it
is a choice about how this deployment is monitored, not a defect to quietly fix. Worth doing when
somebody has a monitoring stack to point at it.

## Verification

Go build, vet, gofmt and the full Go suite (Postgres integration tests included); web typecheck, 82
files / 554 tests, locale parity, and the SPA build.

The rule is tested as a table, on its own, because it *is* the whole policy and a policy buried in an
if-chain inside a middleware is one nobody can test: eleven cases covering the polling reads that
have to stay quiet, the failures and slow reads and mutations that must not, and the page loads that
were logged before and still are.

The middleware is then tested end to end — a failing API request produces a line naming the caller, a
fast successful read produces nothing, and the assets stay silent. The client address is tested from
both sides: an upstream that is not in `trusted_proxies` cannot claim an address, and behind one that
is, the visitor is logged rather than the gateway.

It was also confirmed against a running binary: three report writes and a login appear in the log
with their status, latency and caller, while the `/api/home` reads around them do not.

Three mutations confirmed it: restoring the `/api/` skip fails eight assertions, logging every API
read fails the polling cases, and reading `X-Forwarded-For` directly fails the spoofing case.
