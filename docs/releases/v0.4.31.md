# v0.4.31 — measured, then changed

## Upgrade notes

From v0.4.3 or later — pull and restart. No schema changes and nothing to run by hand. Rolling back
to v0.4.30 is clean.

**The queue's search now runs on the server.** It matches the workflow name, the submitter and the
full inputs of each job's first row, across the whole queue rather than the page the console had
been sent. Results will differ from before in one direction only: it finds more.

**A new build no longer reloads a PWA tab by itself.** Where the service worker used to take over
and refresh the page, it now installs and waits, and the existing "new version" banner is what
applies it. Somebody who never clicks Refresh stays on the build they loaded — which is what the
banner already meant for everyone without the PWA enabled.

**The queue list sends a preview of each run's inputs, not the whole thing.** The full inputs are
unchanged and still shown in the run's detail drawer.

## Changed

**The queue list stopped shipping every prompt, three times a minute.** Measured first, on a 300-job
queue of realistic shape: the response was 1,417 KB per poll — about 470 KB/s for each open tab — for
two clamped lines of text per row. The weight was each job's first-row inputs sent whole, which for
an agent run is its entire prompt.

The store now reads a bounded prefix of that column rather than all of it, and the API sends a
preview clamped per value and then in total. Per value, and measuring is what proved it necessary: a
plain prefix of the JSON keeps whatever the serialiser put first, which was the prompt, so the
preview arrived without the symbol — the one field a person scans for. **1,417 KB → 152 KB, an 89%
cut**, with the identifying fields intact. `internal/app/batch_payload_test.go` builds that queue,
prints the number, and fails if the list ever carries content again.

Bounding the preview would have quietly broken the console's search, which matched against the
inputs it had been sent, so the search moved to the server in the same change — which also resolves
an older ambiguity, where "no results" could mean "nothing matches" or "nothing matches on this
page".

**An unchanged queue answers 304.** The polled endpoints hash the body they were about to send and
revalidate against what the caller already has. A queue in which nothing happened — the normal case
— now costs an empty response, and because the client keeps the object it already had, it costs no
parse, no state update and no re-render either. `/api/` is `no-store`, so nothing along the way
participates: the client holds the tag and sends it back deliberately.

**The header badge stands down while a queue view is open.** It polls the queue summary every 12
seconds so a number can sit beside the button; the queue page and drawer poll the same endpoint
every 3 seconds because they show the queue itself.

## Added

**Reading warms what you are about to open.** Every move within a report — another day on the
timeline, another type, another version — was a full round trip for a payload carrying the whole
body, so the reader waited each time.

What that payload is made of decided the design, so it was measured: on a stock with 28 dates and 4
types the response is 28 KB, of which the report is 27 KB and the navigation 1 KB — 4%. A heavy
skeleton would have meant splitting the endpoint before anything could be warmed; at 4% it can be
reused as it stands, and a test fails if that stops being true.

The two adjacent days are warmed once a report renders — stepping forward or back is the move a
reader makes most — and a type or version tab is warmed when the pointer lands on it. Only the
neighbours: warming the whole strip would download a month of reports nobody asked for. What was
actually read is remembered as well, so returning to it is instant.

Nothing is warmed on a connection the user asked us not to spend, or for a tab nobody is looking at,
and a warm answer only decides whether a view waits — the live request goes out regardless and
replaces it.

## Fixed

**A service worker update could take the page out from under someone.** It called `skipWaiting()` on
install and reloaded from `controllerchange`, so a deploy could interrupt a half-written assistant
prompt, an unsaved settings form or a streaming answer — while the banner beside it existed
precisely so that the user decides when. Two answers to one event, and the louder one destroyed
work.

It was also unsafe on its own terms: activating purges the previous build's cache, and an open tab
still running the old JavaScript then asks for chunks that no longer exist, recoverable only through
the one-shot reload that exists as a fallback.

The worker installs and waits. The banner reports either signal — a different server build, or a
worker ready beside us — and Refresh is what hands over: tell the waiting worker to take control,
reload once it has. Reloading before that would re-run the build being left.

**The audit page could show a row before it was clickable.** It set its data in `.then` and cleared
its loading flag in `.finally` — different microtasks — leaving one render where the rows existed
but the table was still blurred and inert. A single frame in a browser; a race for anything that
acts on a row as soon as it appears.

## Verification

Go build, vet and gofmt; the Go suite; web typecheck, 367 web tests and the SPA build.

Three of the new tests are regression guards with numbers in them rather than assertions about
shape: the queue list's size on a realistic queue, its 304 behaviour, and the proportion of a
reading response that is navigation rather than report.

The two SSRF pre-check tests noted in v0.4.25 still fail on a machine whose resolver answers every
name; unrelated to this release and green on CI.
