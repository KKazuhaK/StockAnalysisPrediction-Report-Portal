# v0.4.26 — a button that stops repeating itself

## Upgrade notes

From v0.4.3 or later — pull and restart. No schema changes, nothing to run by hand, and rolling
back to v0.4.25 is clean: this release changes one attribute on one kind of button.

## Fixed

**Hovering a category or report-type button drew a box beneath it saying the same thing again.**
The box sat hard against the button's bottom edge, so it read as a second control stuck to the
first rather than as a hint — and what it said was exactly the label already on the button.

It was the browser's own tooltip, not one the portal drew. The strip is an antd `Segmented`, and
rc-segmented defaults each item's `title` to its label whenever that label is a plain string, so
every button in these strips carried a `title` that could only restate itself. The strips scroll
sideways rather than truncate, so the label is never clipped and the tooltip never had anything
to add.

Both strips — the category row and the report-type row, on the stock page and the single-report
page — now pass an explicit empty title. Empty rather than absent: absent is what makes
rc-segmented fall back to the label, and an empty attribute also stops a title being inherited
from an ancestor.

The default is deliberately left in place wherever a label *can* be clipped, such as a `block`
Segmented inside a narrow popover. There the native tooltip is the only way to read the rest of
the label, and removing it would cost information instead of noise.

## Verification

Go build, vet and gofmt; the Go suite; web typecheck, 338 web tests and the SPA build. The strip
is asserted in `StockPage.test.tsx` by what a reader would experience — no item carries a tooltip
repeating its own label — rather than by the attribute's mechanism, so the guard survives a change
in how the library derives it.
