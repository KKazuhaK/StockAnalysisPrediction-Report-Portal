# v0.4.35 — a view waits before it tells you there is nothing

## Upgrade notes

From v0.4.3 or later — pull and restart. No schema changes and nothing to run by hand. Rolling back
to v0.4.34 is clean: every change here is in the SPA, and none of it is written down anywhere.

**Nothing you have configured changes.** What changed is what a page is allowed to say before the
server has answered it, and — on the settings pages — what a Save button is allowed to post.

**Two new UI strings**, in all three locales: a generic "could not load this content" and the
line the login page shows while it hands you to an identity provider.

## Fixed

**The queue said it was empty before it had asked.** `/queue` painted the antd empty illustration
under "队列空", over five stat tiles reading 0, from the first frame — for the whole flight of the
first `GET /api/admin/batch/jobs`. Somebody who had submitted a run seconds earlier was told, in as
many words, that the server had nothing queued. `[]` is where a `useState` starts; it is not
something the server said. The same held for the header's queue drawer.

**It was not one page.** A dozen views read their emptiness claim straight off their initial state:
the chat page replaced itself with "尚未配置对话/智能体应用" — configuration advice, given before the
server had spoken — and the apps hub, the batch console, the recurring console and the conversation
rail each announced their own version of nothing. The run dialog went further and printed "队列空闲
—— 立即运行" in green before the queue depth had arrived, which is a sentence people choose 加急 or
定时 on the strength of.

**A settings page could save its own defaults back over your configuration.** v0.4.32's `LoadGate`
fixed this for four settings forms; the same fault was still live wherever a page held a list. The
report-types page posts every row it has, the SSO rules editor PUTs the whole rule array, the
assistant admin card posts `max_concurrent`, and the site and announcement forms post their own
blank fields — all of them reachable, on a slow link or after a failed load, before the page had
seen what it was about to overwrite. An OU's workflow allow-list was one click from being revoked
unseen.

**A failed load wore the face of an answer.** Most of these fetches ended in a bare
`.catch(() => {})`, or a `.finally` with no catch at all, so a dropped request left the false claim
on screen for good — indistinguishable from a real empty result, and with nothing to retry. The home
page was the plainest case: a failed `/api/home` left the card area blank, said nothing, and offered
nothing.

**A 304 was treated as an answer to a question this page had not asked.** The conditional GET behind
the queue poll keeps its ETags in a module-level map that outlives every component using it. The
header badge polls the queue summary and stores its tag; you then click 队列, and the freshly
mounted table sends that tag and is told "nothing changed" — about data it has never held. The stat
tiles stayed on a dash for ever while the badge behind them showed the real count, and on the jobs
list a remount could print "队列空" over the forty jobs the batch console was listing seconds
earlier. The same rule catches an older bug: the jobs URL carries the search text, so clearing the
search box asked with a tag stored before the current rows, and the 304 left the filtered results on
screen as the unfiltered list.

**The header's queue badge could not tell zero from unknown.** A count of 0 draws no badge, and so
did a count nobody had asked for yet — so "nothing is queued" and "the summary has not arrived" were
the same picture, and on a summary request that keeps failing it was the first of those,
permanently. Until the count is real the badge is now a muted dot: enough that the header is not
claiming zero, quiet enough not to read as an alert. It was also polling through the same shared
tag store, so a queue view that tagged the summary first could leave the badge with no count at all.

**The compare dialog re-fetched its own list in a loop.** Both of its effects listed `t` as a
dependency while using it only to word an error, so a new `t` identity re-fetched the comparable
editions, which re-rendered, which fetched again. It only ever settled because the answer usually
matched what was already there.

## Added

**The SSO button says it is going somewhere.** Clicking a provider on the login page sets
`window.location` and returns — after which nothing on the page changes until the browser decides to
leave, which on a slow link is several seconds of a button that looks like it did not work. The
natural response is to press it again, which starts a second handshake over the first. The pressed
button now spins, the other providers and the password form go quiet rather than inviting a race,
and a line underneath names where you are being taken. Force-SSO gets the same notice instead of
showing a login card for a beat and then vanishing. The step-up dialog in 账号 carries the same
button doing the same thing, so it says the same.

## Notes

`LoadGate` — v0.4.32's answer for a settings form — now covers the list surfaces too, with a `title`
for views whose failure is not about settings. Only a first load gates: a poll that fails once rows
are on screen leaves them there, because they are still the last thing the server said, and a
refresh after a save no longer blanks the page it just saved. A background refresh that fails takes
nothing away — sending a chat message no longer risks replacing the conversation rail with an error.

The queue's stat tiles hold a dash rather than a zero until the summary lands. A dash is not a
number; a wall of zeros looks like a page that has finished loading on an idle queue.

Back from an identity provider restores the login page from the browser's bfcache with its React
state intact, so the redirect notice clears on `pageshow` rather than leaving a spinner on a
handshake that is already over.

configured; and the login page's redirect notice, including its bfcache reset.
